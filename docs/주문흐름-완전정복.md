## 0. 먼저 알아야 할 기초 개념 10개

코드를 보기 전에 이 단어들만 알면 됩니다. 어렵게 생각하지 마세요.

| 개념 | 한 줄 설명 | 비유 |
|---|---|---|
| **프론트엔드(frontend)** | 손님이 보는 화면. Vue로 만듦 | 식당의 "홀" |
| **백엔드(backend)** | 화면 뒤에서 계산하고 저장하는 서버. Spring으로 만듦 | 식당의 "주방" |
| **DB(데이터베이스)** | 데이터를 영구 보관하는 곳. MySQL | 식당의 "창고" |
| **Vue 컴포넌트** | 화면 한 조각. `.vue` 파일 하나 = 화면 하나 | 레고 블록 |
| **`ref` / 반응형** | "이 값이 바뀌면 화면도 자동으로 다시 그려라" | 자동 새로고침 |
| **Pinia store** | 여러 화면이 **같이 쓰는 데이터 창고** | 공용 화이트보드 |
| **API** | 프론트가 백엔드에게 말 거는 창구 (`/api/...`) | 주방에 넣는 주문서 |
| **axios / http** | API를 부르는 도구 (심부름꾼) | 홀과 주방 사이 벨 |
| **JSON** | 데이터를 담는 글자 형식 `{ "이름": "값" }` | 주문서 양식 |
| **쿠키(cookie)** | 브라우저가 잠깐 기억하는 작은 메모 | 포스트잇 |

이 프로젝트의 큰 원칙 하나만 기억하세요:

> **화면(프론트)은 DB를 직접 못 만진다. 반드시 백엔드에게 부탁(API)한다.**
> 손님이 주방 냉장고를 직접 열지 않고, 종업원에게 주문서를 주는 것과 같습니다.

## 1. 전체 그림

```
┌─────────────┐   /api 요청    ┌─────────────┐   SQL     ┌──────────┐
│  프론트엔드   │ ────────────▶ │   백엔드     │ ───────▶ │   DB      │
│  (Vue :5173) │ ◀──────────── │ (Spring:8080)│ ◀─────── │(MySQL3307)│
└─────────────┘   JSON 응답    └─────────────┘   결과     └──────────┘
      │                                                 
      └── 손님이 고르는 중의 값은 DB가 아니라 "쿠키"에 임시 저장
```

- **왜 셋으로 나눠요?** 각자 역할이 달라서예요. 화면은 예쁘게 보여주기만, 백엔드는 계산·검증·저장만, DB는 보관만. 나눠두면 한 곳을 고쳐도 다른 곳이 안 망가집니다.
- **왜 장바구니는 DB에 안 넣어요?** 키오스크 손님은 회원가입을 안 해요. 고르는 중인 임시 데이터를 DB에 넣으면 지저분해집니다. 그래서 **결제 버튼을 누르는 순간에만** 백엔드로 보내서 DB에 저장합니다. 그 전까지는 브라우저 쿠키에만 담아둡니다.

## 2. 파일 지도

주문 흐름에 관련된 파일만 추렸습니다.

```
frontend/src/
├── main.js                  앱 시작점 (Vue·Pinia·라우터 켜기)
├── App.vue                  가장 바깥 껍데기 (화면을 갈아끼우는 틀)
├── router/index.js          "이 주소로 오면 이 화면을 보여줘" 규칙
│
├── stores/                  ★ 공용 데이터 창고 (Pinia)
│   ├── cart.js              장바구니 (쿠키에 저장)
│   └── orderFlow.js         지금 몇 단계인지 + 화면이 쓰는 모든 값·함수
│
├── utils/cookie.js          쿠키에 읽고 쓰는 도구
├── api/http.js              백엔드 부르는 심부름꾼 (axios)
├── services/menuService.js  메뉴 데이터 가져오는 함수
├── data/menuDummy.js        상품 더미 데이터 (아직 DB 대신 씀)
│
└── views/kiosk/
    ├── OrderView.vue        ★ 주문 전체를 감싸는 화면 (단계별로 갈아끼움)
    ├── PaymentScanView.vue  손님 휴대폰이 QR 스캔하면 열리는 결제 페이지
    └── steps/               ★ 단계별 화면 조각들
        ├── OrderTypeStep.vue        매장/포장
        ├── ProductStep.vue          메뉴 선택
        ├── ContainerStep.vue        컵/콘
        ├── FlavorStep.vue           맛 선택
        ├── CartStep.vue             장바구니 확인
        ├── CustomerPaymentStep.vue  포인트/결제
        └── ReceiptStep.vue          영수증 (결제 후)

backend/src/main/java/com/kiosk/
├── kiosk/menu/        메뉴 조회 API
├── kiosk/customer/    회원 조회 API
├── kiosk/order/       주문 저장 API
├── kiosk/payment/     결제 API
└── kiosk/receipt/     영수증 조회 + 프린터 출력 API
```

**화면 = `views/kiosk/steps/`의 `.vue` 파일들**, **데이터·로직 = `stores/orderFlow.js`** 이렇게 딱 나뉩니다.
화면은 "버튼 보여주고 클릭 받기"만 하고, 실제 일은 전부 `orderFlow`에게 시킵니다.

## 3. 앱이 처음 켜질 때

### 3-1. `main.js` — 시동 걸기

```js
import { createApp } from 'vue'
import { createPinia } from 'pinia'
import App from './App.vue'
import router from './router'

const app = createApp(App)   // Vue 앱을 만든다
app.use(createPinia())        // 공용 창고(Pinia) 기능을 켠다
app.use(router)               // 주소별 화면전환(라우터) 기능을 켠다
app.mount('#app')             // index.html의 <div id="app">에 화면을 붙인다
```

> 이 파일은 딱 한 번 실행돼요. "Vue 켜고, 창고 켜고, 라우터 켜고, 화면 붙여!" 이게 전부입니다.

### 3-2. `router/index.js` — 주소 → 화면 규칙

```js
routes: [
  { path: '/',            component: HomeView },          // 광고 화면
  { path: '/kiosk/order', component: OrderView },         // 주문 전체
  { path: '/pay/:token',  component: PaymentScanView },   // 폰 결제 페이지
  { path: '/admin/login', component: AdminLoginView }
]
```

- `path`는 **주소**, `component`는 그 주소에서 보여줄 **화면**입니다.
- `/pay/:token`의 `:token`은 **빈칸**이에요. `/pay/abc123`으로 오면 `token = "abc123"`이 됩니다. (결제 QR마다 다른 토큰이 들어감)

### 3-3. `HomeView.vue` — 시작 화면

```vue
<template>
  <main class="home">
    <h1>Kiosk</h1>
    <RouterLink to="/kiosk/order">주문 시작하기</RouterLink>
  </main>
</template>
```

- `<RouterLink to="/kiosk/order">`는 **클릭하면 주소를 `/kiosk/order`로 바꾸는 링크**입니다.
- 주소가 바뀌면 라우터 규칙에 따라 `OrderView.vue`가 화면에 뜹니다. → 주문 시작!

## 4. 핵심 두 창고: cart와 orderFlow

주문 흐름의 심장은 이 두 파일이에요. 화면들은 전부 여기서 값을 읽고 함수를 부릅니다.

### 4-1. `stores/cart.js` — 장바구니 (쿠키에 저장)

장바구니에 담긴 것들을 보관합니다. **특별한 점: 값이 바뀔 때마다 쿠키에 저장**해요.

```js
const EMPTY_STATE = () => ({
  orderType: null,            // 'DINE_IN'(매장) 또는 'TAKEOUT'(포장)
  customerMobileNumber: null, // 회원 전화번호
  usedPoints: 0,              // 사용할 포인트
  items: []                   // 담은 메뉴 목록 ★
})
```

**`items` 배열 안의 메뉴 하나는 이렇게 생겼어요:**

```js
{
  id: "자동생성된 고유번호",
  productId: 105,          // 어떤 상품인지 (파인트)
  productName: "파인트",
  unitPrice: 12000,
  quantity: 1,
  containerType: "CUP",    // 컵/콘/없음
  spoonCount: 0,
  dryIceMinutes: null,
  flavors: [               // 고른 맛들
    { flavorId: 1, flavorName: "초코", selectionOrder: 1, quantity: 1 },
    { flavorId: 2, flavorName: "바닐라", selectionOrder: 2, quantity: 1 }
  ]
}
```

**getters (계산해서 보여주는 값):**

```js
getters: {
  totalCount: (state) => state.items.reduce((합, item) => 합 + item.quantity, 0),
  //   → 담은 메뉴 총 개수
  amountBeforeDiscount: (state) => state.items.reduce((합, item) => 합 + item.unitPrice * item.quantity, 0),
  //   → 할인 전 총액 (단가 × 수량을 전부 더함)
  totalAmount() {
    return Math.max(0, this.amountBeforeDiscount - this.usedPoints)
    //   → 실제 낼 돈 = 총액 - 사용 포인트 (0원 밑으로는 안 내려감)
  }
}
```

> `reduce`는 "배열을 하나씩 돌면서 합계를 구하는" 자바스크립트 함수예요.
> `state.items.reduce((합, item) => 합 + item.quantity, 0)` = "0에서 시작해서, 각 item의 quantity를 합에 더해라".

**actions (값을 바꾸는 함수들):**

```js
addItem(item)        // 장바구니에 메뉴 추가 (+ 쿠키 저장)
updateItem(id, 변경) // 특정 메뉴 수정
removeItem(id)       // 특정 메뉴 삭제
setOrderType(타입)   // 매장/포장 설정
setCustomer(번호)    // 회원 번호 설정
setUsedPoints(점수)  // 사용 포인트 설정
clear()              // 전부 비우기 (다음 손님용)
```

**쿠키에 저장하는 원리 (`persist` 함수):**

```js
function persist(state) {
  setCookie('kiosk_cart', JSON.stringify({ ...장바구니내용... }))
  //  JSON.stringify = 객체를 글자로 바꾼다 (쿠키엔 글자만 저장 가능)
}
```

그리고 앱이 켜질 때는 반대로 쿠키에서 읽어옵니다:

```js
state: () => loadFromCookie()   // 쿠키에 저장된 게 있으면 그걸로 시작
```

> **핵심 원리:** 값이 바뀌면 → 쿠키에 저장. 새로고침하면 → 쿠키에서 복원.
> 그래서 실수로 새로고침해도 장바구니가 안 날아갑니다.
> 단, `cookie.js`에서 **만료일을 안 정한 "세션 쿠키"**라 브라우저를 닫으면 사라져요.
> (다음 손님이 이전 손님 장바구니를 물려받으면 안 되니까 일부러 이렇게 함)

### 4-2. `stores/orderFlow.js` — 지금 몇 단계인가 + 화면의 모든 것

이게 제일 큽니다. **"지금 어느 화면인지"**와 **화면이 쓰는 모든 값·함수**가 여기 다 있어요.

가장 중요한 값은 `step`입니다:

```js
state: () => ({
  step: 'orderType',   // ★ 지금 단계. 이 값에 따라 화면이 바뀐다
  categories: [],       // 카테고리 목록 (아이스크림/커피)
  products: [],         // 상품 목록
  flavors: [],          // 맛 목록
  selectedCategory: null,  // 지금 보고 있는 탭
  selectedProduct: null,   // 방금 고른 상품
  selectedFlavorIds: [],   // 고르는 중인 맛들
  containerType: 'NONE',   // 컵/콘
  customer: null,          // 조회된 회원 정보
  orderId: null,           // 주문이 저장되면 받는 번호
  qrInfo: null,            // 결제 QR 정보
  receipt: null,           // 영수증 데이터
  ...
})
```

`step`이 바뀌면 화면이 바뀝니다. 이걸 `OrderView.vue`가 이렇게 씁니다:

```vue
<OrderTypeStep       v-if="orderFlow.step === 'orderType'" />
<ProductStep    v-else-if="orderFlow.step === 'product'" />
<ContainerStep  v-else-if="orderFlow.step === 'container'" />
<FlavorStep     v-else-if="orderFlow.step === 'flavor'" />
<CartStep       v-else-if="orderFlow.step === 'cart'" />
<CustomerPaymentStep v-else-if="orderFlow.step === 'customer'" />
<ReceiptStep    v-else-if="orderFlow.step === 'receipt'" />
```

> `v-if`는 "조건이 맞으면 이 화면을 보여줘"라는 Vue 문법이에요.
> `step`이 `'flavor'`면 `FlavorStep`만 보이고 나머지는 숨습니다.
> **즉 주문 흐름은 `step`이라는 값 하나를 바꿔가며 화면을 갈아끼우는 것**입니다.

`OrderView.vue`가 처음 뜰 때 `orderFlow.init()`을 부르는데, 이게 메뉴 데이터를 백엔드에서 불러옵니다:

```js
async init() {
  // 이전 손님 흔적을 전부 초기화하고...
  this.step = cart.orderType ? 'product' : 'orderType'
  // 메뉴를 백엔드에서 동시에 3개 불러온다
  const [categories, products, flavors] = await Promise.all([
    fetchCategories(), fetchProducts(), fetchFlavors()
  ])
  this.categories = categories
  this.products = products
  this.flavors = flavors
}
```

> `await`는 "이 작업이 끝날 때까지 기다려"라는 뜻. 네트워크 요청은 시간이 걸리니까요.
> `Promise.all([...])`는 "3개를 동시에 요청하고 다 올 때까지 기다려" (빠르게).

## 5. 주문 흐름 한 화면씩 따라가기

이제 실제로 손님이 클릭하는 순서대로 따라갑니다. **각 화면마다: 무엇이 보이나 → 클릭하면 무슨 함수가 도나 → 데이터가 어떻게 변하나** 순서로 봅니다.

### 단계 1: 매장/포장 — `OrderTypeStep.vue`

**화면:** "매장에서 드시나요, 포장하시나요?" 팝업 + 버튼 2개.

```vue
<button @click="orderFlow.selectOrderType('DINE_IN')">매장</button>
<button @click="orderFlow.selectOrderType('TAKEOUT')">포장</button>
```

**클릭하면** `orderFlow.selectOrderType('DINE_IN')`이 실행됩니다:

```js
selectOrderType(orderType) {
  const cart = useCartStore()
  cart.setOrderType(orderType)  // ① 장바구니에 매장/포장 저장 (→ 쿠키에도)
  this.step = 'product'          // ② 다음 단계로! 화면이 ProductStep으로 바뀜
}
```

**데이터 변화:** `cart.orderType = 'DINE_IN'`, `orderFlow.step = 'product'`

---

### 단계 2: 메뉴 선택 — `ProductStep.vue`

**화면:** 위에 카테고리 탭(아이스크림/커피), 아래에 상품 목록.

```vue
<!-- 카테고리 탭 -->
<button
  v-for="category in orderFlow.categories"
  :class="{ active: orderFlow.selectedCategory?.categoryId === category.categoryId }"
  @click="orderFlow.selectedCategory = category">
  {{ category.categoryName }}
</button>

<!-- 상품 목록 -->
<li v-for="product in orderFlow.visibleProducts">
  <button @click="orderFlow.selectProduct(product)">
    {{ product.productName }} - {{ product.basePrice.toLocaleString() }}원
  </button>
</li>
```

> `v-for`는 "배열을 하나씩 돌면서 반복해서 그려라". 카테고리가 2개면 탭 버튼 2개, 상품이 8개면 버튼 8개가 자동으로 생깁니다.
> `{{ }}` 안의 값은 화면에 글자로 표시돼요. `toLocaleString()`은 `12000`을 `12,000`으로 콤마 찍어주는 함수.

**탭을 누르면** `selectedCategory`만 바뀌고, `visibleProducts`가 자동으로 그 카테고리 상품만 걸러줍니다:

```js
// getters
visibleProducts: (state) => state.products.filter(
  (p) => p.categoryId === state.selectedCategory?.categoryId
)
//  filter = "조건 맞는 것만 남겨라". 지금 탭의 카테고리 상품만 남김.
```

**상품을 누르면** `orderFlow.selectProduct(product)`가 실행됩니다. 여기가 **똑똑한 갈림길**이에요:

```js
selectProduct(product) {
  this.editingItemId = null
  this.resetFlavorStepState(product)   // 맛 선택용 상태 초기화

  if (product.containerPolicy === 'CUP_OR_CONE') {
    this.step = 'container'   // 컵/콘 둘 다 되는 상품 → 용기 선택 화면으로
    return
  }
  this.proceedPastContainer()  // 그 외 → 용기 선택 건너뜀
}

proceedPastContainer() {
  if (!this.selectedProduct.requiresFlavorSelection && !this.selectedProduct.isLarge) {
    // 맛도 옵션도 없는 상품(예: 아메리카노) → 바로 장바구니에 담고 확인 화면으로
    this.addCurrentSelectionToCart()
    this.step = 'cart'
    return
  }
  this.step = 'flavor'   // 맛 골라야 하는 상품 → 맛 선택 화면으로
}
```

**왜 이렇게 갈라지나요?** 상품마다 필요한 단계가 다르기 때문이에요:
- **싱글레귤러**(컵/콘 가능) → 용기 선택 O, 맛 선택 O
- **파인트**(컵만) → 용기 선택 X, 맛 선택 O
- **아메리카노**(옵션 없음) → 용기·맛 다 건너뛰고 바로 장바구니

이 판단 기준은 **상품 데이터에 들어있는 `containerPolicy`, `requiresFlavorSelection`, `isLarge`** 값이에요. (`menuDummy.js` 또는 DB에서 옴)

```js
  const cart = useCartStore()
  // 고른 맛 배열을 만들고
```

**① 전화번호로 회원 조회** — "조회" 버튼 → `lookupCustomer()`:

```js
async lookupCustomer() {
  const { data } = await http.get(`/customers/${this.mobileNumberInput}`)
```

> 여기서 처음으로 **백엔드를 부릅니다**. `http.get(...)`이 심부름꾼이에요.

**② 포인트 조절** — `-1000/+100/최대` 버튼들:

```js
adjustUsedPoints(delta) {   // delta = -1000, +100 등
  const next = Math.min(
    this.customer.pointBalance,      // 보유 포인트보다 많이 못 씀
    cart.amountBeforeDiscount,        // 결제 금액보다 많이 못 씀
    Math.max(0, cart.usedPoints + delta)  // 0 밑으로 안 내려감
  )
  cart.setUsedPoints(next)   // 확정
}
```

**③ 예상 적립 포인트** — 자동 계산되는 값:

```js
estimatedEarnedPoints(state) {
  if (cart.usedPoints > 0) return 0   // 포인트를 쓰면 적립은 안 줌
  const grade = state.customer?.grade ?? 'FRIEND'
  return Math.floor(cart.totalAmount * (EARN_RATE[grade] ?? 0))
  //  등급별 적립률: FRIEND 3% / FAMILY 5% / VIP 8%
}
```

**④ 결제 버튼** — `startPayment()`. 여기가 **프론트에서 백엔드로 주문을 보내는 순간**입니다:

```js
async startPayment() {

  this.checkoutPayload = {
    branchId: 1,
    orderType: cart.orderType,
    customerMobileNumber: cart.customerMobileNumber,
    usedPoints: cart.usedPoints,
    language: 'ko',
    items: cart.items.map((item) => ({

      containerType: item.containerType,
      spoonCount: item.spoonCount,
      dryIceMinutes: item.dryIceMinutes,
      flavorIds: item.flavors.map((f) => f.flavorId)

  this.orderId = data.orderId   // 백엔드가 준 주문번호 저장

  await this.requestQr()

```

> **여기가 이 프로젝트의 하이라이트예요.** 지금까지 쿠키에만 있던 장바구니가,
> 결제 버튼을 누르는 이 순간 **백엔드로 전송되어 DB에 저장**됩니다.
> `map`으로 장바구니 형식을 백엔드 형식(`flavorIds`만 보냄 등)으로 변환하는 것도 눈여겨보세요.

## 6. 결제와 영수증

### 6-1. QR 생성 — `requestQr()`

```js
async requestQr() {
  const { data } = await http.post('/payments/qr', { orderId: this.orderId })
  this.qrInfo = data
  this.qrDataUrl = await QRCode.toDataURL(`${window.location.origin}/pay/${data.qrToken}`)
  //  ↑ QR 이미지를 만든다. 내용은 "지금주소/pay/토큰"
  this.startPolling(data.qrToken)  // 결제됐는지 계속 확인 시작
}
```

- `qrToken`은 이 결제만의 **고유 열쇠**예요. 백엔드가 만들어줍니다.
- QR 안에는 `http://지금주소/pay/토큰` 주소가 들어갑니다. 손님이 폰으로 찍으면 이 주소가 열려요.
- `window.location.origin`은 "지금 이 화면의 주소"예요. 그래서 PC에서 접속한 주소가 QR에 그대로 담깁니다.

### 6-2. 폰이 QR을 스캔하면 — `PaymentScanView.vue`

손님 폰에서 `/pay/토큰`이 열리고, 이 화면이 뜹니다:

```js
async confirmPayment() {
  const { data } = await http.post(`/payments/${route.params.token}/confirm`)
  //  백엔드에 "이 결제 완료 처리해줘"
  status.value = data
}
```

> `route.params.token`이 주소의 `:token` 자리에 있던 값이에요.
> "결제 완료 처리" 버튼을 누르면 백엔드가 그 주문을 **결제완료(PAID)**로 바꿉니다.

### 6-3. 키오스크는 어떻게 결제된 걸 아나 — 폴링(polling)

키오스크 화면은 폰에서 무슨 일이 일어났는지 몰라요. 그래서 **2초마다 백엔드에 물어봅니다**:

```js
startPolling(qrToken) {
  this.pollTimer = setInterval(async () => {   // 2초마다 반복
    const { data } = await http.get(`/payments/${qrToken}`)  // "결제됐어?"
    this.paymentStatus = data.paymentStatus
    if (data.paymentStatus === 'PAID') {       // 됐다!
      this.stopPolling()                        // 그만 물어봄
      this.qrInfo = null                        // QR 팝업 닫기
      await this.loadReceipt()                  // 영수증 데이터 받아오기
      this.step = 'receipt'                     // 영수증 화면으로!
      this.printReceipt()                       // 프린터로 출력
    }
  }, 2000)
}
```

> `setInterval(함수, 2000)` = "2초(2000밀리초)마다 이 함수를 실행해라".
> 폰이 결제를 완료하면, 다음 폴링에서 `PAID`를 보고 영수증 화면으로 넘어갑니다.
> 이게 **"손님 폰과 키오스크 화면이 따로 있는데 어떻게 연동되나?"**의 답이에요.

### 6-4. 영수증 화면 — `ReceiptStep.vue`

```js
// 영수증 데이터 받아오기
async loadReceipt() {
  const { data } = await http.get(`/orders/${this.orderId}/receipt`)
  this.receipt = data   // 주문번호, 상품, 금액, 결제정보가 다 들어있음
```

영수증 화면은 `receipt` 데이터를 종이 영수증처럼 그려줍니다. "완료"를 누르면 장바구니를 비우고 처음으로 돌아가 다음 손님을 받습니다.

### 6-5. 영수증이 실제로 프린터에서 나오는 원리


- 브라우저가 프린터를 직접 못 불러요(보안 정책 CORS 때문). 그래서 **우리 백엔드가 대신** 강사님 PC의 프린터 서비스(8888)로 요청을 보냅니다.

## 7. 백엔드는 요청을 어떻게 처리하나

백엔드는 항상 **3층 구조**예요. 요청이 위에서 아래로 흐릅니다:

```
Controller (API 입구)  →  Service (실제 로직)  →  Repository (DB 접근)
```

- **Controller**: "어떤 주소로 어떤 요청이 오면 받는다"만 정함
- **Service**: 실제 계산·검증·저장 로직
- **Repository**: DB에 SQL을 날리는 도구 (우리가 SQL을 안 짜도 됨)

### 예시: 결제 버튼 → 주문 저장 (`/api/orders/checkout`)

**① Controller — 요청을 받기만:**

```java
@RestController
@RequestMapping("/api/orders")
public class OrderController {
    @PostMapping("/checkout")
    public OrderCheckoutResponse checkout(@RequestBody OrderCheckoutRequest request) {
        return orderService.checkout(request);   // Service에게 넘김
    }
}
```

> `@PostMapping("/checkout")` = "POST /api/orders/checkout 요청이 오면 이 함수 실행".
> `@RequestBody`는 "프론트가 보낸 JSON을 자바 객체로 바꿔서 넣어줘"라는 뜻.

**② Service — 실제 일 (핵심 로직):**

```java
@Transactional   // 중간에 실패하면 전부 취소 (돈 관련이라 중요)
public OrderCheckoutResponse checkout(OrderCheckoutRequest request) {
    // 1. 지점 확인
    Branch branch = branchRepository.findById(request.branchId()).orElseThrow(...);

    // 2. 회원 찾기 (없는 번호면 FRIEND 등급으로 자동 가입)
    Customer customer = customerRepository.findByMobileNumber(...)
        .orElseGet(() -> customerRepository.save(Customer.builder()...build()));

    // 3. ★ 금액을 백엔드가 다시 계산 (프론트가 보낸 가격을 안 믿음!)
    int amountBeforeDiscount = 0;
    for (OrderItemRequest itemRequest : request.items()) {
        Product product = productRepository.findById(itemRequest.productId()).orElseThrow(...);
        amountBeforeDiscount += product.getBasePrice();   // DB의 진짜 가격으로 합산
    }

    // 4. 포인트 검증 후 최종 금액 계산
    int usedPoints = Math.min(요청포인트, 보유포인트, 금액);
    int finalAmount = amountBeforeDiscount - usedPoints;

    // 5. 주문 저장 (주문 → 주문상품 → 주문상품맛 순서로)
    Order order = orderRepository.save(Order.builder()...build());
    for (...) {
        OrderItem orderItem = orderItemRepository.save(...);   // 상품 저장
        for (Long flavorId : ...) {
            orderItemFlavorRepository.save(...);                // 맛 저장
        }
    }

    // 6. 프론트에 결과 돌려줌 (주문번호, 금액)
    return new OrderCheckoutResponse(order.getOrderId(), order.getOrderNumber(), ...);
}
```

> **왜 금액을 다시 계산해요?** 프론트(브라우저)는 손님이 조작할 수 있어요.
> 누가 개발자도구로 가격을 100원으로 바꿔서 보낼 수도 있죠. 그래서 **백엔드가 DB의 진짜 가격으로 다시 계산**합니다. 이게 "결제 위변조 방지"의 기본이에요.

**저장 구조가 3단인 이유:** 한 주문에 여러 상품, 한 상품에 여러 맛이 들어가니까요.

```
주문(Order) 1개
 ├─ 주문상품(OrderItem): 파인트
 │   ├─ 주문상품맛(OrderItemFlavor): 초코
 │   ├─ 주문상품맛: 바닐라
 │   └─ 주문상품맛: 민트
 └─ 주문상품(OrderItem): 아메리카노  (맛 없음)
```

### 결제 확정 (`/api/payments/{token}/confirm`)

폰이 이걸 부르면 `PaymentService.confirm()`이:
1. QR이 만료됐는지 확인
2. 결제 상태를 `PAID`로 변경, 승인번호 생성
3. 주문 상태도 `PAID`로 변경
4. **포인트 정산**: 사용한 포인트는 차감, (포인트 안 썼으면) 등급별 적립률로 적립

```java
if (order.getUsedPoints() > 0) {
    earnedPoints = 0;   // 포인트 쓴 결제는 적립 없음
} else {
    int rate = switch (customer.getGrade()) {   // 등급별 적립률
        case FRIEND -> 3; case FAMILY -> 5; case VIP -> 8;
    };
    earnedPoints = order.getFinalAmount() * rate / 100;
}
customer.setPointBalance(보유 - 사용 + 적립);   // 최종 포인트 반영
```

## 8. 데이터 전체 여정 요약 (한 장)

```
[손님]                    [프론트: step 변화]         [저장되는 곳]
───────────────────────────────────────────────────────────────
광고 화면 터치         →   /kiosk/order 이동
매장/포장 선택         →   step: orderType→product     쿠키(cart.orderType)
상품 선택(파인트)      →   step: product→container/flavor
컵/콘 선택            →   step: container→flavor       orderFlow.containerType
맛 3개 선택           →   (flavor 화면 유지)            orderFlow.selectedFlavorIds
"장바구니 담기"       →   step: flavor→cart            쿠키(cart.items에 추가) ★
장바구니 확인         →   step: cart→customer
번호 조회            →   ─ GET /customers/{번호} ──▶  백엔드 조회 (DB)
포인트 조절           →                                쿠키(cart.usedPoints)
"결제" 클릭          →   ─ POST /orders/checkout ──▶  ★ DB에 주문 저장!
                      →   ─ POST /payments/qr ──────▶  DB에 결제(QR) 생성
                          QR 팝업 표시 + 2초마다 폴링
[폰] QR 스캔·결제완료  →   ─ POST /payments/{t}/confirm▶ DB: 주문 PAID, 포인트 정산
[키오스크] 폴링이 PAID 감지 →   step: customer→receipt
                      →   ─ GET  /orders/{id}/receipt ▶ 영수증 데이터
                      →   ─ POST /orders/{id}/print ──▶ 백엔드 → 프린터(8888) → 출력
"완료" 클릭          →   cart.clear() + / 로 복귀      쿠키 삭제 (다음 손님)
```

### 딱 3가지만 기억하세요

1. **화면 전환 = `orderFlow.step` 값 바꾸기.** 화면들은 `step`을 보고 자기가 나올지 말지 정한다.
2. **고르는 중 = 쿠키(cart), 결제 순간 = DB.** 회원가입 없는 키오스크라 임시값은 쿠키에만 담다가, 결제할 때 한 번에 백엔드로 보내 DB에 저장한다.
3. **프론트는 DB를 직접 못 만진다.** 항상 `http.get/post`로 백엔드 API를 부르고, 백엔드가 `Controller→Service→Repository`를 거쳐 DB를 처리한다.

## 9. 화면별 DB 연관 지도

이제 **각 화면이 DB의 어떤 테이블·컬럼과 연결되는지**를 정리합니다.
먼저 큰 원칙 하나를 다시 짚어요:

> **주문 흐름의 앞부분(매장/포장 ~ 장바구니)은 DB를 거의 안 건드립니다.**
> 이때 고른 값은 전부 쿠키에만 있어요. DB에 **읽으러** 가는 건 "메뉴/맛/회원 조회"뿐이고,
> DB에 **저장**하는 건 "결제 버튼을 누른 순간"이 처음입니다.

읽기/쓰기를 이렇게 표시할게요: **📖 읽기(SELECT)** · **✏️ 쓰기(INSERT/UPDATE)**

### 이 주문 흐름에 등장하는 8개 테이블

| 테이블 | 한글 | 무엇을 담나 |
|---|---|---|
| `branch` | 지점 | 매장 정보 (지점명, 주소 등) |
| `category` | 카테고리 | 아이스크림/커피 분류 |
| `product` | 상품(사이즈) | 싱글레귤러·파인트 등 판매 단위 + 가격 |
| `flavor` | 맛 | 초코·바닐라 등 맛 정보 |
| `customer` | 고객 | 전화번호·등급·포인트 |
| `order` | 주문 | 주문 1건의 전체 정보 |
| `order_item` | 주문상품 | 주문에 담긴 상품 하나하나 |
| `order_item_flavor` | 주문상품맛 | 상품에서 고른 맛 하나하나 |
| `payment` | 결제 | QR·결제상태·승인번호 |

---

### 단계 1: 매장/포장 — `OrderTypeStep.vue`

- **DB 접근: 없음.** 고른 값(DINE_IN/TAKEOUT)은 쿠키에만 저장됩니다.
- 이 값은 나중에 결제할 때 `order` 테이블의 **`order_type`** 컬럼에 들어갑니다.

### 단계 2: 메뉴 선택 — `ProductStep.vue`

- 📖 **`flavor`** — 맛 목록을 `GET /api/flavors`로 미리 불러옴 (init 단계에서)
  - 쓰는 컬럼: `flavor_id`, `flavor_name`, 그리고 조건으로 `is_visible=1 AND sale_status='ON_SALE'`
- 📖 **`product`** (지금은 더미, 원래는 DB) — 상품 목록
  - 화면이 쓰는 컬럼: `product_id`, `category_id`, `product_name`, `base_price`, `requires_flavor_selection`, `selectable_flavor_count`, `container_policy`, `is_large`
  - 이 컬럼들이 **다음 단계를 결정**합니다: `container_policy`가 `CUP_OR_CONE`이면 용기 화면을 거치고, `requires_flavor_selection`이 1이면 맛 화면으로 갑니다.
- 📖 **`category`** (지금은 더미) — 상단 탭. 컬럼: `category_id`, `category_name`

> **왜 상품은 더미(menuDummy.js)를 써요?** 지금은 개발 편의로 프론트에 상품 목록을 하드코딩해뒀어요.
> 단, `db/init/02-seed.sql`로 DB에도 **똑같은 `product_id`(101~)**를 넣어놨습니다. 그래야 결제할 때
> 백엔드가 그 id로 `product`를 조회할 수 있거든요. 나중에 `menuService.js`의 주석만 바꾸면 완전히 DB 연동됩니다.

### 단계 3: 용기 선택 — `ContainerStep.vue`

- **DB 접근: 없음.** 고른 컵/콘은 쿠키에만.
- 이 화면이 **뜰지 말지**는 `product.container_policy` 값으로 정해집니다.
- 고른 값은 나중에 `order_item` 테이블의 **`container_type`** 컬럼에 들어갑니다.

### 단계 4: 맛 선택 — `FlavorStep.vue`

- 📖 **`flavor`** — 단계 2에서 이미 불러온 맛 목록을 그대로 보여줌 (추가 조회 없음)
- 진행률 `2/3`의 분모(3)는 **`product.selectable_flavor_count`** 컬럼 값이에요.
- 대용량 상품의 숟가락/드라이아이스 입력칸은 `product.is_large`가 1일 때만 뜹니다.
- 고른 맛들은 나중에 `order_item_flavor` 테이블의 **`flavor_id`, `selection_order`** 로 저장됩니다.

### 단계 5: 장바구니 확인 — `CartStep.vue`

- **DB 접근: 없음.** 여기까지 담은 모든 건 오직 쿠키(`kiosk_cart`)에만 있습니다.
- 화면에 보이는 상품·맛·금액은 전부 쿠키에서 읽어와 그린 것입니다.

> 이 지점이 중요해요. **장바구니 전용 DB 테이블이 없습니다.** 회원가입 없는 키오스크라
> 굳이 DB에 임시 저장할 필요가 없어서, 쿠키 JSON 하나로 처리하는 게 이 프로젝트의 설계입니다.

### 단계 6: 포인트/결제 — `CustomerPaymentStep.vue`

여기서 **처음으로 DB에 저장(쓰기)**이 일어납니다. 3가지 동작을 나눠 봐요.

**(1) 전화번호 조회** — `GET /api/customers/{번호}`
- 📖 **`customer`** — 컬럼: `mobile_number`(검색), `grade`(등급), `point_balance`(보유 포인트)
- 화면의 `등급`, `보유 포인트P`가 이 컬럼들에서 옵니다.

**(2) "결제" 버튼** — `POST /api/orders/checkout`
- 📖 **`branch`** — `branch_id`로 지점 확인
- 📖 **`product`** — 보낸 `productId`로 조회해서 **진짜 가격(`base_price`)으로 금액 재계산**
- 📖 **`flavor`** — 보낸 `flavorId`로 맛 확인
- ✏️ **`customer`** — 없는 번호면 새로 INSERT (자동 가입, `grade`=FRIEND, `point_balance`=0)
- ✏️ **`order`** — 주문 1건 INSERT. 들어가는 컬럼:
  | 컬럼 | 값의 출처 |
  |---|---|
  | `branch_id` | 지점 (지금은 1 고정) |
  | `customer_id` | 조회/가입된 고객 |
  | `order_number` | 백엔드가 생성 (ORD+시간+랜덤) |
  | `order_type` | 단계 1에서 고른 매장/포장 |
  | `order_status` | `PENDING_PAYMENT` (결제 전) |
  | `used_points` | 사용 포인트 |
  | `amount_before_discount` | 할인 전 금액 (DB 가격으로 계산) |
  | `discount_amount` | 할인액(=사용 포인트) |
  | `final_amount` | 최종 결제 금액 |
- ✏️ **`order_item`** — 담은 상품마다 1줄씩 INSERT. 주요 컬럼:
  `order_id`, `product_id`, **`product_name_snapshot`**, **`unit_price_snapshot`**, `quantity`, `item_total`, `container_type`, `spoon_count`, `dry_ice_minutes`
- ✏️ **`order_item_flavor`** — 상품에서 고른 맛마다 1줄씩 INSERT. 주요 컬럼:
  `order_item_id`, `flavor_id`, **`flavor_name_snapshot`**, `selection_order`

> **📸 스냅샷(snapshot) 컬럼이 왜 있나요?** `product_name_snapshot`, `unit_price_snapshot`, `flavor_name_snapshot`은
> **주문 당시의 이름·가격을 복사해서 박아두는** 컬럼이에요. 나중에 파인트 가격이 12,000→13,000으로 바뀌어도,
> **예전 영수증에는 그때 낸 12,000원이 그대로 남아야** 하니까요. `product_id`만 저장하고 가격은 매번
> product에서 읽어오면, 가격이 바뀌는 순간 과거 주문 기록이 다 틀어집니다. 그래서 "그 순간의 값"을 따로 저장합니다.

**(3) QR 생성** — `POST /api/payments/qr`
- ✏️ **`payment`** — 결제 1건 INSERT. 컬럼: `order_id`, `payment_method`(QR), `payment_status`(`QR_CREATED`), `qr_token`(고유 열쇠), `qr_expires_at`(5분 뒤), `requested_amount`

### 결제 확정 — `PaymentScanView.vue` (폰) → `POST /api/payments/{token}/confirm`

여기서 여러 테이블이 한꺼번에 **UPDATE**됩니다:
- ✏️ **`payment`** — `payment_status`→`PAID`, `paid_amount`, `approval_number`, `paid_at` 채움
- ✏️ **`order`** — `order_status`→`PAID`, `earned_points`(적립 포인트) 채움
- ✏️ **`customer`** — `point_balance` 갱신 (사용분 차감 + 적립분 더함)

### 영수증 — `ReceiptStep.vue`

- 📖 **영수증 조회** `GET /api/orders/{id}/receipt` — 아래를 전부 읽어서 합침:
  - `branch`(지점명 `branch_name`), `order`(주문번호·금액·적립), `order_item`(상품들·스냅샷), `order_item_flavor`(맛들), `payment`(결제수단·승인번호·시각)
- 📖 **프린터 출력** `POST /api/orders/{id}/print` — 같은 데이터를 읽어서 프린터 형식
  `{orderNo, orderItem, price, orderDate}`로 만들어 강사님 프린터(8888)로 보냄

### 한눈에 보는 화면 ↔ 테이블 표

| 화면 | 📖 읽는 테이블 | ✏️ 쓰는 테이블 |
|---|---|---|
| 매장/포장 | — | — (쿠키만) |
| 메뉴 선택 | `flavor`, `product`*, `category`* | — |
| 용기 선택 | — | — (쿠키만) |
| 맛 선택 | `flavor` | — |
| 장바구니 | — | — (쿠키만) |
| 포인트/결제 (조회) | `customer` | — |
| 포인트/결제 (결제) | `branch`, `product`, `flavor` | `customer`, `order`, `order_item`, `order_item_flavor`, `payment` |
| 결제 확정 (폰) | `payment`, `order`, `customer` | `payment`, `order`, `customer` |
| 영수증 | `branch`, `order`, `order_item`, `order_item_flavor`, `payment` | — |

> `*` 표시(`product`, `category`)는 지금은 더미 데이터라 실제로는 DB를 안 거치지만,
> DB에도 같은 값이 있고 `menuService.js`만 바꾸면 바로 DB 연동됩니다.

## 부록: 자주 나오는 자바스크립트/Vue 문법 사전

| 문법 | 뜻 |
|---|---|
| `const x = ...` | 값 x를 정의 (안 바뀌는 상자) |
| `let x = ...` | 값 x를 정의 (바뀔 수 있는 상자) |
| `async / await` | "이거 끝날 때까지 기다려" (네트워크 요청 등) |
| `배열.map(x => ...)` | 배열의 각 항목을 변형해서 새 배열 |
| `배열.filter(x => ...)` | 조건 맞는 항목만 남김 |
| `배열.reduce((합,x)=>..., 0)` | 배열을 하나의 값(합계 등)으로 압축 |
| `JSON.stringify(객체)` | 객체 → 글자 |
| `JSON.parse(글자)` | 글자 → 객체 |
| `{{ 값 }}` (Vue) | 화면에 값을 글자로 표시 |
| `v-if="조건"` (Vue) | 조건이 참일 때만 이 요소를 보여줌 |
| `v-for="x in 배열"` (Vue) | 배열을 반복해서 그림 |
| `@click="함수"` (Vue) | 클릭하면 함수 실행 |
| `:class="{ active: 조건 }"` (Vue) | 조건이 참이면 active 스타일 적용 |
| `?.` (옵셔널 체이닝) | 값이 없어도(null) 에러 안 나게 안전하게 접근 |
| `??` (널 병합) | 왼쪽이 없으면 오른쪽 기본값 사용 |
