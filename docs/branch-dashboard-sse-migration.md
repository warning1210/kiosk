# 지점 대시보드 실시간 갱신: 폴링 → SSE 전환

## 배경

지점 관리자 화면에서 세 곳이 각자 `setInterval` 폴링으로 새 주문/공지를 확인하고 있었다.

| 컴포넌트 | 파일 | 폴링 대상 | 주기 | 언제 동작하나 |
|---|---|---|---|---|
| 신규 주문 뱃지 | `BranchSidebar.vue` → `useNewOrderAlert.js` | `GET /branch/orders` | 3초 | 지점 관리자 화면 어디에 있든(사이드바가 항상 떠 있으므로) |
| 대시보드 | `DashboardView.vue` | `GET /branch/orders`, `GET /branch/inventory`, `GET /branch/notices` | 3초 | `/branch/dashboard` 화면에 있을 때만 |
| 실시간 주문 처리 | `OrdersView.vue` | `GET /branch/orders?activeOnly=true` | 2초 | `/branch/orders` 화면에 있을 때만 |

(`OrderListView.vue`, 날짜별 주문 이력 조회 화면은 원래도 폴링 없이 1회성 조회였다 - 실시간성이 필요 없는 과거 이력 화면이라 이번에도 그대로 뒀다.)

문제: 매장이 한산해서 몇 시간째 주문이 하나도 없어도, 화면만 켜져 있으면 정확히 같은 빈도로 계속 조회 요청을 쐈다. 실제 변경 여부와 요청량이 완전히 무관했다.

## 변경 내용

- 백엔드에 `GET /api/branch/events/stream` (SSE, `SseEmitter`) 추가 — 지점별로 연결을 붙잡아두고, 실제로 아래 이벤트가 발생할 때만 `order`/`notice` 이벤트를 그 지점(또는 전 지점)에 보낸다. (`branch/dashboard/service/BranchEventPublisher.java`)
  - `order`: 아래 3곳에서 발행
    - `PaymentService.markPaidAndComplete()` — 주문이 결제 완료될 때 (QR/카드/현금/포인트 결제 전부 이 메서드를 거친다)
    - `BranchOrderService.updateOrderStatus()` — 지점 직원이 조리중/준비완료/취소 등 상태를 바꿀 때
    - `OrderCleanupService.autoCancelOldOrders()` — 처리 안 된 주문을 매분 자동취소하는 배치가 실제로 취소 처리를 했을 때
  - `notice`: `HqNoticeService.create()/update()` — 본사가 공지사항을 작성/수정할 때 (전 지점 브로드캐스트)
- 프론트는 `useBranchEventStream.js`(신규, 탭당 EventSource 연결 1개를 공유) 를 통해 이벤트를 구독하고, 이벤트가 왔을 때만 기존 `load()`/`refresh()`를 호출한다. 위 세 화면의 `setInterval`을 전부 제거했다.

### 부수적으로 발견해 같이 고친 버그

`BranchOrderService.updateOrderStatus()`가 `order.setOrderStatus(...)`만 하고 **`orderRepository.update(order)`를 호출하지 않고 있었다.** JPA였다면 트랜잭션 커밋 시 변경 감지(dirty checking)로 자동 반영됐겠지만, MyBatis는 그런 자동 flush가 없다 - 즉 지점 직원이 "조리중"/"완료" 버튼을 눌러도 **DB에는 전혀 반영되지 않고 있었다.** 화면상 낙관적 업데이트(`o.status = status`)로 눌렀을 때는 바뀐 것처럼 보였지만 새로고침하면 원래대로 돌아가는 상태였을 것이다. SSE 작업 중 이 메서드에 이벤트 발행을 추가하다가 발견해서 `orderRepository.update(order)` 호출과 완료 처리 시 `orderCompletedAt` 기록을 같이 추가했다.
- 브라우저 기본 `EventSource`는 커스텀 헤더(Authorization)를 못 보내므로, 이 스트림 엔드포인트에 한해 토큰을 쿼리 파라미터로 받는다(`?token=...`). 다른 `/api/branch/**`는 기존 그대로 헤더 방식.
- 연결이 끊기면 브라우저가 EventSource를 자동 재연결한다(별도 재시도 로직 불필요).

### 데스크톱 알림

지점 관리자 탭이 어딘가 열려만 있으면(다른 탭 보는 중, 창 최소화 등 백그라운드 상태 포함) 새 결제 건이 들어왔을 때 브라우저 데스크톱 알림이 뜨도록 `useBranchEventStream.js`에 추가했다.

- 결제가 실제로 확정된 순간(`PaymentService.markPaidAndComplete`)에만 `newOrder` 이벤트를 별도로 쏜다. 상태변경(조리중/완료)이나 자동취소는 여전히 `order` 이벤트만 쏘고 `newOrder`는 안 쏜다 - 안 그러면 "새 주문 왔어요"가 실제로는 상태변경일 때도 잘못 뜬다.
- `document.hidden`(탭이 안 보이는 상태)일 때만 알림을 띄운다 - 화면을 보고 있으면 뱃지 갱신만으로 충분해서 알림까지 겹치지 않게 했다.
- 탭이 아예 닫혀 있으면 못 띄운다 (SSE 연결 자체가 탭이 열려 있어야 유지되므로). 브라우저/탭이 완전히 닫힌 상태에서도 알림을 받으려면 Service Worker 기반 Web Push(VAPID 키 발급, 백엔드에 구독 저장/발송 인프라 필요)로 별도 작업이 필요하다 - 이번 범위에는 포함하지 않았다.

### 배포 인프라: nginx 버퍼링/타임아웃

nginx는 기본적으로 업스트림 응답을 다 모았다가 흘려보낸다(`proxy_buffering on`). SSE처럼 끝나지 않는 스트림에 이 기본값을 그대로 두면 이벤트가 클라이언트로 영영 안 나간다 — 로컬 개발(vite 프록시)은 버퍼링을 안 해서 문제없이 동작했지만, 배포 환경(`frontend/nginx.conf`)의 기존 `/api/` location을 그대로 썼다면 실제 EC2 배포 시 SSE가 조용히 안 되는 상태였을 것이다. 그래서 `/api/branch/events/` 전용 location을 추가해 `proxy_buffering off`, `proxy_read_timeout 1h`로 분리했다. 백엔드도 `BranchEventPublisher`에 25초 주기 `ping` 하트비트를 추가해 죽은 연결을 빨리 정리하고 중간 프록시의 idle timeout도 피하게 했다.

**알려진 제약**:
- SSE 연결 목록은 서버 인스턴스 메모리에 있다(`ConcurrentHashMap`). 서버를 여러 대로 수평 확장하면 다른 인스턴스에 붙은 클라이언트에는 이벤트가 전달되지 않는다 — 트래픽 규모상 지금은 문제없고, 필요해지면 Redis pub/sub 등으로 브로드캐스트 계층을 넣으면 된다.
- 재고 입고 확인(`confirmStockReceipt`)은 이번엔 이벤트를 안 걸었다 — 주문 결제 시 자동 차감(`deductForOrder`)은 `order` 이벤트에 얹혀 커버되지만, 지점 재고 화면에서 수동으로 실물 입고 처리하는 시점은 아직 폴링 시절과 동일하게 다음 `order`/`notice` 이벤트나 화면 재진입 때까지 반영이 늦을 수 있다.
- 스트림 연결용 토큰을 쿼리 파라미터로 받기 때문에(`?token=...`), 다른 `/api/branch/**` 엔드포인트(Authorization 헤더 방식, 기본 로그 포맷에 안 남음)와 달리 이 토큰은 nginx access log에 평문으로 남을 수 있다. 토큰이 12시간 만료라 위험도는 낮지만, 로그 보존/접근 정책상 민감하면 access log에서 `token=` 쿼리스트링을 마스킹하는 log_format을 별도로 두는 게 안전하다.
- 스트림 연결은 최초 접속 시 한 번만 토큰을 검증한다. 이후 토큰이 만료돼도(12시간) 이미 열려있는 연결 자체는 끊기지 않는다 - 탭을 계속 켜두면 만료 이후에도 그 지점의 라이브 업데이트를 계속 받는다. 조회 전용 스트림이라 위험은 낮지만, 엄격하게 하려면 하트비트 시점에 토큰 재검증을 추가할 수 있다.

## 요청량 비교

전제: 폴링 주기 3초 = 시간당 1,200회.

### 수정 전 (setInterval 폴링)

| 상황 | 시간당 요청 수 | 계산 |
|---|---|---|
| 지점 관리자 화면 아무 곳(대시보드·주문처리 제외)에 1시간 체류 | **1,200회** | 사이드바 알림만 (3초 주기 orders × 1,200) |
| 대시보드 화면에 1시간 체류 | **4,800회** | 사이드바(1,200) + 대시보드(3초 주기 orders+inventory+notices × 3종 × 1,200) |
| 실시간 주문 처리 화면에 1시간 체류 | **3,000회** | 사이드바(1,200) + 주문처리(2초 주기 orders × 1,800) |

→ **실제 신규 주문이 0건이어도 완전히 동일한 양**의 요청이 나간다. 새벽 시간대·한산한 매장일수록 순수 낭비 비율이 커진다. 특히 실시간 주문 처리 화면은 2초 주기라 세 화면 중 가장 공격적으로 폴링하고 있었다.

### 수정 후 (SSE)

| 항목 | 비용 |
|---|---|
| 연결 유지 | 탭당 HTTP 연결 1개 (지속 연결, 반복 요청 아님) |
| 실제 데이터 재조회 | `order` 이벤트당 최대 4회 GET(사이드바 1 + 대시보드 3), `notice` 이벤트당 최대 3회 GET(대시보드만) — **오직 실제 결제/공지 발생 시에만** |

예시: 영업시간 중 피크타임에 시간당 결제 20건 + 공지 0건, 대시보드 화면에 1시간 체류한다고 가정하면:

- 재조회 요청: 20건 × 4회 = **최대 80회/시간**
- 수정 전(4,800회) 대비 **약 98% 감소**
- 주문이 없는 새벽/한산한 시간대는 폴링 시절엔 여전히 4,800회였지만, SSE는 **0에 수렴**한다 (연결 유지 비용만 존재).

핵심은 폴링은 요청량이 화면 체류 시간에 비례하고, SSE는 요청량이 실제 비즈니스 이벤트(결제/공지) 발생 빈도에 비례한다는 것 — 트래픽이 "구경하는 시간"이 아니라 "실제로 뭔가 바뀐 횟수"를 따라가게 됐다.

## 검증

- `mvn compile` / `mvn test` — 기존 17개 테스트 전부 통과, 컴파일 에러 없음 (SSE 관련 신규 자동 테스트는 추가하지 않음 — `SseEmitter` 통합 동작은 실제 브라우저/서버 연결로 확인하는 게 더 신뢰도 높아서 수동 확인으로 갈음).
- 수동 확인 필요: 브랜치 로그인 → 대시보드 진입 → 네트워크 탭에서 `events/stream` 연결이 하나만 유지되는지, 키오스크에서 결제를 완료했을 때 대시보드가 즉시(폴링 지연 없이) 갱신되는지, 본사에서 공지 작성 시 지점 화면에 반영되는지.
