A01:2025

접근 통제 실패 (Broken Access Control)

로그인한 사람이 "볼 자격이 있는 것만" 보게 하는 통제가 무너지는 문제

① 토큰 버전을 관리해 로그아웃된 사용자의 기존 토큰이 더 이상 유효하지 않도록 차단
📖 이런 상황이 있었습니다

지점 관리자가 매장 계산대 옆 공용 PC에서 관리자 화면에 로그인했다가, 일을 마치고 로그아웃 버튼을 누르고 자리를 떠납니다. 보통은 이걸로 끝났다고 생각합니다.

그런데 기존 로그아웃은 브라우저에 저장된 토큰을 지우는 것이 전부였고 서버에는 아무 요청도 보내지 않았습니다. 로그인 토큰은 서버에 세션을 저장하지 않는 방식이라, 서명만 맞으면 발급 후 12시간 동안 계속 유효했습니다. 즉 로그아웃 직전에 개발자도구에서 토큰을 한 번 복사해 둔 사람은, 그 뒤로 브라우저도 비밀번호도 없이 그 계정으로 매출·재고·주문을 열람할 수 있었습니다. 점장 본인이 다시 로그인해도, 브라우저를 밀어도 막을 방법이 없었습니다.

📍 상황매장 공용 PC에서 지점 관리자 로그인
→
🚨 문제로그아웃해도 복사해둔 토큰이 12시간 그대로 통함
→
🔧 적용토큰에 세대 번호를 서명해 넣고 로그아웃 시 +1
→
✅ 결과로그아웃 즉시 기존 토큰 전부 401
문제가 있던 코드 — AdminSidebar.vue (로그아웃)

  localStorage.removeItem('hq-session')   // 브라우저에서 문자열만 삭제
  router.replace('/branch/login')          // 서버에는 알리지 않음
}
// → 서버가 발급한 토큰은 만료(12시간)까지 그대로 살아있다
해결 — AdminTokenService.java (세대 카운터)
// adminId -> 현재 토큰 버전. 없으면 0버전.
private final Map<Long, Integer> tokenVersions = new ConcurrentHashMap<>();

/** 이 관리자에게 발급된 모든 토큰을 즉시 무효화한다(로그아웃, 탈취 대응). */
public void revokeAll(Long adminId) {
    tokenVersions.merge(adminId, 1, Integer::sum);   // 원자적 +1
}

public String issue(Long adminId) {
    // 발급 당시의 버전을 payload에 함께 넣어 서명한다 → 값을 되돌리면 서명이 깨진다
    return sealed(adminId + ":" + currentVersion(adminId) + ":" + expiresIn(VALID_DURATION));
}

// 검증할 때: 서명 확인 → 만료 확인 → 버전 대조
if (Integer.parseInt(parts[offset + 1]) != currentVersion(adminId)) return null;
신설 — LogoutController.java (로그아웃 API)
@PostMapping("/logout")
public void logout(@RequestHeader(value = "Authorization", required = false) String authorization,
                   HttpServletResponse response) {
    authCookie.clear(response);                       // 쿠키 삭제 (JS는 못 지운다)
    if (authorization == null || !authorization.startsWith("Bearer ")) return;

    Long adminId = adminTokenService.verify(authorization.substring(7));
    if (adminId != null) adminTokenService.revokeAll(adminId);   // 버전 +1
}

💡 핵심 정리
  • 로그아웃은 브라우저에서 지우는 것이 아니라 서버에서 무효화하는 것이어야 합니다
  • 버전 번호도 서명 대상이라, 공격자가 값을 되돌리면 서명이 깨져 거부됩니다
  • 한 사람의 로그아웃이 다른 관리자 토큰에는 영향을 주지 않습니다 (계정별 카운터)
  • 인증 경로가 이미 매 요청 계정을 조회하고 있어 추가 비용이 사실상 없습니다
⚠️ 알고 있는 한계

버전 카운터를 서버 메모리에 두었기 때문에 서버를 재시작하면 무효화 상태가 초기화됩니다. DB 컬럼으로 옮기면 재시작에도 유지되지만, 팀이 공유하는 개발 DB에 스키마 변경이 필요해 이번에는 메모리 방식을 선택했습니다.

A02:2025

보안 설정 오류 (Security Misconfiguration)

프로그램은 정상적으로 작동하지만, 보안 설정이 허술해서 공격받기 쉬워지는 문제

① 관리자·키오스크 화면에서만 API 응답을 읽도록 CORS 제한
📖 이런 상황이 있었습니다

관리자 화면에 상품, 재고, 주문 정보를 보여주려면 프론트엔드가 관리자 화면 → 상품·재고·주문 API 호출을 보내야 합니다. 개발 중에는 프론트엔드 주소와 포트가 자주 바뀌었습니다. 주소가 바뀔 때마다 CORS 설정을 수정하는 것이 번거로워서 모든 출처(*)를 허용해 두었습니다. 덕분에 어느 개발 주소에서든 API 응답을 바로 확인할 수 있었습니다.

하지만 운영 서버에서도 모든 출처를 허용하면, 우리 서비스와 관계없는 사이트에도 응답을 보여주게 됩니다. 예를 들어 관리자가 로그인한 채 공격자가 보낸 링크를 열면, 공격 사이트의 스크립트가 관리자 브라우저를 통해 키오스크 API를 호출할 수 있습니다. 이때 CORS가 모든 출처를 허용하고 있으면 브라우저가 그 사이트에도 응답을 공개하여 상품·재고·주문 정보가 노출될 수 있습니다.

그래서 개발 편의를 위한 전체 허용 설정은 없애고, 실제 관리자 화면과 키오스크 주소만 허용 목록에 넣었습니다. 이제 공격 사이트가 API 요청을 보내더라도 등록된 주소가 아니면 브라우저가 응답 내용을 읽지 못합니다. CORS는 요청 자체를 막는 기능이 아니므로, 로그인 인증과 관리자 권한 검사는 API에서 별도로 확인합니다.

🚨 문제점 분석

모든 Origin을 허용하면 로그인한 관리자가 악성 사이트를 열었을 때 그 사이트의 스크립트도 관리자 API 응답을 읽을 수 있습니다. CORS는 인증을 대신하지 않으므로 허용 Origin 제한과 API 인증·권한 검사를 함께 적용해야 합니다.

📍 상황브라우저에서 관리자 API 호출
→
🚨 문제모든 Origin을 허용해 악성 사이트에도 응답 공개
→
🔧 적용환경별 CORS 화이트리스트 사용
→
✅ 결과미등록 Origin에는 허용 헤더를 반환하지 않음
문제가 있었던 코드 — SecurityConfig.java
CorsConfiguration configuration = new CorsConfiguration();
configuration.addAllowedOriginPattern("*"); // 모든 Origin 허용
configuration.setAllowCredentials(true);
configuration.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE", "OPTIONS"));

// 운영 환경에서도 악성 사이트에 CORS 응답을 허용할 수 있음
🔧 적용 사항

1. application.yml — 개발·운영 환경별로 허용할 관리자·키오스크 Origin 목록을 분리해 설정.
2. SecurityConfig.java — 모든 출처를 허용하던 * 설정을 제거하고 setAllowedOriginPatterns(originPatterns)로 허용 목록만 등록.
3. SecurityConfig.java — 자격 증명 사용 여부와 허용 메서드·헤더를 명시해 등록되지 않은 Origin에는 CORS 허용 헤더를 반환하지 않도록 변경.

SecurityConfig.java — 실제 적용 코드
@Value("${app.cors.allowed-origin-patterns}")
private List<String> originPatterns;

CorsConfiguration configuration = new CorsConfiguration();
configuration.setAllowedOriginPatterns(originPatterns); // * 대신 허용 목록
configuration.setAllowCredentials(true);
configuration.setAllowedMethods(List.of("GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS"));
configuration.setAllowedHeaders(List.of("Authorization", "Content-Type"));

❌ 적용 전 — 모든 출처 허용되어 미등록 출처도 통과
Origin: https://evil.example

→ 등록하지 않은 사이트도 응답을 읽을 수 있음
✅ 적용 후 — 등록된 출처만 허용, 허용 목록 외 차단
Origin: https://evil.example

→ 브라우저가 응답 사용을 차단
→ 운영 프론트엔드 Origin만 정상 허용
✨ 결론

운영 환경의 API 응답은 등록된 프론트엔드에서만 읽을 수 있게 되었으며, API 인증과 권한 검사는 별도의 방어선으로 계속 유지합니다.

💡 핵심 정리
  • 모든 출처 허용 대신 환경별로 관리하는 허용 목록을 사용합니다
  • 자격 증명을 사용하는 요청은 특히 출처를 좁게 제한해야 합니다
  • CORS는 브라우저 정책이므로 API 인증과 권한 검사는 별도로 유지해야 합니다
② Nginx 보안 헤더로 클릭재킹과 잘못된 파일 실행 방지
📖 이런 상황이 있었습니다

Nginx는 화면과 API를 정상적으로 전달하고 있었지만, 브라우저가 지켜야 할 보안 규칙은 보내지 않고 있었습니다. 이 상태에서는 공격 사이트가 관리자 화면을 투명한 프레임으로 덮어 사용자가 엉뚱한 버튼을 누르게 하거나, 브라우저가 파일 형식을 잘못 판단해 실행할 수 있습니다.

그래서 Nginx 응답에 Content-Security-Policy, X-Frame-Options, X-Content-Type-Options 등의 헤더를 추가했습니다. 이제 브라우저는 허용된 리소스만 불러오고, 다른 사이트가 관리자 화면을 프레임에 넣거나 파일 형식을 임의로 판단하는 동작을 차단합니다.

🚨 문제점 분석

보안 헤더가 없으면 다른 사이트가 관리자 화면을 프레임에 삽입하거나 브라우저가 파일 형식을 임의로 추측할 수 있어 클릭재킹과 의도하지 않은 콘텐츠 실행 위험이 커집니다.

📍 상황Nginx가 프론트엔드와 API 응답 제공
→
🚨 문제브라우저 보안 정책 헤더가 없음
→
🔧 적용CSP·Frame·nosniff 등 헤더 설정
→
✅ 결과클릭재킹·임의 리소스 실행 위험 감소
문제가 있었던 코드 — nginx.conf
server {
  listen 80;

  location / {
    try_files $uri $uri/ /index.html;
  }

  # CSP, X-Frame-Options, nosniff 등 보안 헤더가 없음
}
🔧 적용 사항

1. nginx.conf — Content-Security-Policy를 추가해 허용할 리소스 출처와 프레임 삽입 범위를 제한.
2. nginx.conf — X-Frame-Options와 X-Content-Type-Options를 추가해 클릭재킹과 MIME 타입 추측을 차단.
3. nginx.conf — Referrer-Policy와 Permissions-Policy를 모든 응답에 always 옵션으로 적용.

nginx.conf — 실제 적용 코드
add_header Content-Security-Policy
  "default-src 'self'; object-src 'none'; frame-ancestors 'self'" always;
add_header X-Frame-Options "SAMEORIGIN" always;
add_header X-Content-Type-Options "nosniff" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
add_header Permissions-Policy "camera=(), microphone=(), geolocation=()" always;
🧪 실제 테스트 실행
❌ 적용 전 — 보안 정책 헤더 없음
$ curl -I https://kiosk.example

→ Content-Security-Policy: 없음
→ X-Frame-Options: 없음
→ X-Content-Type-Options: 없음
→ 외부 프레임 삽입과 MIME 추측을 제한하지 못함
✅ 적용 후 — 보안 헤더 응답 확인
$ curl -I https://kiosk.example

→ Content-Security-Policy: default-src 'self' ...
→ X-Frame-Options: SAMEORIGIN
→ X-Content-Type-Options: nosniff
→ 브라우저 보안 정책 정상 적용
✨ 결론

브라우저가 허용된 리소스와 표시 방식만 사용하도록 제한해 클릭재킹과 잘못된 파일 실행 위험을 줄였습니다.

💡 핵심 정리
  • CSP로 허용할 리소스 출처와 프레임 삽입 범위를 제한합니다
  • nosniff로 브라우저가 파일 형식을 추측해 실행하지 못하게 합니다
  • 헤더는 취약한 코드를 고치는 대신이 아니라 피해를 줄이는 추가 방어선입니다
⚠️ 검증 범위와 한계

검증 범위: SecurityConfig의 허용 Origin 목록과 Nginx의 CSP·X-Frame-Options·nosniff 등 보안 헤더 설정을 확인합니다. 브라우저에서 허용된 Origin에는 CORS 헤더가 나오고, 미등록 Origin에는 나오지 않는지도 비교합니다.

한계: CORS는 브라우저가 응답을 읽는 것을 제한할 뿐 curl·Postman 요청 자체를 막지 않습니다. API 인증·권한 검사와 HTTPS는 별도로 필요하며, CSP도 XSS 취약 코드 자체를 제거하는 방어는 아닙니다.

A03:2025

소프트웨어 공급망 실패 (Software Supply Chain Failures)

라이브러리·빌드·배포 등 소프트웨어를 만들고 전달하는 모든 과정에서 발생할 수 있는 보안 문제

① 시크릿(비밀번호·API 키)을 Git에 올리지 않기 — .env.example
📖 이런 상황이 있었습니다

아이스크림 키오스크를 만들면서 데이터베이스 비밀번호, 결제 API 키, Firebase 키 같은 중요한 비밀값들을 코드와 함께 Git 저장소에 그대로 올렸고, GitHub나 GitLab 같은 플랫폼에 코드가 올라가면 이를 모니터링하는 악성 봇들의 표적이 되기 때문에, 비밀번호와 키가 해커에게 탈취되어 결제 API가 무단으로 사용되는 문제가 생길 수 있습니다. 심지어 나중에 지워도 이미 커밋 기록에 영구적으로 남아있어 완전히 없앨 수가 없습니다.

암호화 실패 (Cryptographic Failures)

민감한 값이 보호되지 않은 채 저장·전송·기록되는 문제 — 암호를 안 쓰는 것뿐 아니라 잘못 쓰는 것도 포함됩니다

① 1분짜리 스트림 전용 티켓을 사용해 실시간 알림 토큰이 서버 로그에 노출되지 않도록 방지
📖 이런 상황이 있었습니다

지점 대시보드는 새 주문이 들어오면 즉시 알림을 띄우기 위해 SSE(Server-Sent Events)로 서버와 연결을 유지합니다. 그런데 브라우저의 EventSource는 커스텀 헤더를 보낼 수 없습니다. 그래서 로그인 토큰을 주소창(URL 쿼리 파라미터)에 실어 보낼 수밖에 없었습니다.

문제는 Tomcat 액세스 로그가 쿼리스트링을 포함한 요청 주소 전체를 기록한다는 점이었습니다. 즉 12시간 동안 그 지점 계정으로 뭐든 할 수 있는 토큰이 로그 파일에 평문으로 30일간 보관되고 있었습니다. 로그를 볼 수 있는 사람이라면 누구나 그 값을 복사해 쓸 수 있는 상태였습니다.

🚨 문제점 분석

${} 문자열 치환은 외부 입력을 SQL 본문에 직접 결합하므로, 공격 문자열이 조회 조건 자체를 바꿀 수 있습니다.

인젝션 (Injection)

사용자가 입력한 값이 SQL이나 로그의 형식을 바꾸는 명령처럼 처리되는 문제

① MyBatis 파라미터 바인딩을 사용해 상품 번호가 SQL 문장으로 직접 실행되지 않도록 방지
📖 이런 상황이 있었습니다

아이스크림 키오스크에서 상품 번호를 입력하면 데이터베이스에서 해당 상품의 재고를 찾는 기능을 만들었습니다. 처음에는 화면에서 받은 번호를 MyBatis의 ${itemId}로 SQL 문장에 바로 붙이는 방식을 생각했습니다.

테스트하면서 상품 번호 자리에 999999 OR 1=1을 넣어 보니, 이 값이 단순한 상품 번호가 아니라 SQL 조건문의 일부로 합쳐질 수 있다는 문제가 있었습니다. 이렇게 되면 조건이 항상 참이 되어 요청한 상품 외의 재고까지 조회될 수 있습니다.

        CustomerRepository.class.getName() + ".findByMobileNumberHash");

        .contains("mobile_number_hash=?")
        .doesNotContain(attack);

@Service
public class HqUploadService {

    private static final Set ALLOWED_EXTENSIONS = Set.of("png", "jpg", "jpeg");

    // 확장자별로 허용되는 실제 MIME 타입 (매직바이트 기준)
    private static final Map> ALLOWED_MIME_TYPES_BY_EXTENSION = Map.of(
            "png", Set.of("image/png"),
            "jpg", Set.of("image/jpeg"),
            "jpeg", Set.of("image/jpeg")
    );

    private static final ContentInfoUtil CONTENT_INFO_UTIL = new ContentInfoUtil();

    @Value("${app.upload.dir}")
    private String uploadDir;

    public String store(MultipartFile file) {
        if (file == null || file.isEmpty()) {
            throw new IllegalArgumentException("업로드할 파일이 없습니다.");
        }

        String originalName = file.getOriginalFilename();

        String extension = getExtension(originalName);

        if (!ALLOWED_EXTENSIONS.contains(extension)) {
            throw new IllegalArgumentException(
                    "PNG, JPG, JPEG 파일만 업로드할 수 있습니다."
            );
        }

        try {
            byte[] content = file.getBytes();

            validateActualContentType(content, extension);

            Path uploadPath = Paths.get(uploadDir)
                    .toAbsolutePath()
                    .normalize();

            // 파일이 없으면 생성
            Files.createDirectories(uploadPath);

            // UUID 기반 신규 파일명 생성
            String storedFilename = UUID.randomUUID()
                    + "."
                    + extension;

            Path target = uploadPath.resolve(storedFilename)
                    .normalize();

            // 최종 경로 검증 (추가 방어)
            if (!target.startsWith(uploadPath)) {
                throw new SecurityException("잘못된 파일 경로입니다.");
            }

            Files.write(target, content);

            return "/uploads/" + storedFilename;

        } catch (IOException e) {
            throw new RuntimeException(
                    "이미지 업로드에 실패했습니다.",
                    e
            );
        }
    }


// 파일 확장자가 아닌 실제 바이너리 시그니처(매직바이트)로 이미지 타입을 검증한다.
    private void validateActualContentType(byte[] content, String extension) throws IOException {
        ContentInfo contentInfo = CONTENT_INFO_UTIL.findMatch(content);
        String mimeType = contentInfo != null ? contentInfo.getMimeType() : null;

        Set allowedMimeTypes = ALLOWED_MIME_TYPES_BY_EXTENSION.get(extension);

        if (mimeType == null || allowedMimeTypes == null || !allowedMimeTypes.contains(mimeType)) {
            throw new IllegalArgumentException(
                    "파일 내용이 PNG, JPG, JPEG 이미지 형식이 아닙니다."
            );
        }
    }

@Transactional
public PaymentStatusResponse confirm(String qrToken) {
    Payment payment = findByToken(qrToken);
    if (payment.getPaymentStatus() == PaymentStatus.PAID) {
        return toStatusResponse(payment);
    }

    if (payment.getQrExpiresAt().isBefore(LocalDateTime.now())) {
        payment.setPaymentStatus(PaymentStatus.EXPIRED);
        paymentRepository.save(payment);
        throw new ResponseStatusException(HttpStatus.GONE, "QR 유효시간이 지났습니다. 다시 생성해주세요.");
    }

    // ← 게이트웨이 검증 없이 그 자리에서 바로 결제를 승인 처리

    markPaidAndComplete(payment);   // PAID 처리 + 포인트 적립 + 쿠폰 소진 + 재고 차감

    return toStatusResponse(payment);
}

import java.util.concurrent.atomic.AtomicReference;

import org.springframework.stereotype.Component;

// 로그인류 엔드포인트(HQ/지점 로그인, Firebase 세션 교환)에 대해 클라이언트 IP 기준으로
// 짧은 시간 안에 너무 많은 요청이 오면 429로 막는다. Turnstile은 "사람인지"만 걸러낼 뿐
// 같은 사람의 무제한 재시도(무차별 대입)까지 막지는 못하므로 그 방어선을 여기서 채운다.

// 매장 전체가 한 번에 묶이지 않도록 임계치를 넉넉하게 잡았다.
// Spring Boot가 Filter 빈을 자동으로 서블릿 컨테이너에 등록해주므로 별도 설정은 필요 없다.
@Slf4j
@Component
public class LoginRateLimitFilter extends OncePerRequestFilter {

    private static final Set<String> LIMITED_PATHS = Set.of(
            "/api/hq-auth/login",
            "/api/branch-auth/db-login",
            "/api/branch-auth/firebase-session"
    );

    private static final int MAX_ATTEMPTS = 10;  // 10번 허용
    private static final Duration WINDOW = Duration.ofMinutes(5);  //5분

    private record Window(int count, Instant resetAt) {}

    private final ConcurrentHashMap<String, AtomicReference<Window>> attempts = new ConcurrentHashMap<>();

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response, FilterChain chain)
            throws ServletException, IOException {
    	if (!"POST".equals(request.getMethod())
    	        || !LIMITED_PATHS.contains(request.getRequestURI())) {
            chain.doFilter(request, response);
            return;
        }

        String ip = request.getRemoteAddr();
        AtomicReference<Window> ref = attempts.computeIfAbsent(ip,
                k -> new AtomicReference<>(new Window(0, Instant.now().plus(WINDOW))));

        Window updated = ref.updateAndGet(w -> Instant.now().isAfter(w.resetAt())
                ? new Window(1, Instant.now().plus(WINDOW))
                : new Window(w.count() + 1, w.resetAt()));

        if (updated.count() > MAX_ATTEMPTS) {
            // 무차별 대입 탐지용 보안 이벤트 기록. 윈도우당 처음 차단되는 순간에만 남겨
            // 공격 트래픽이 로그 자체를 폭주시키는 것을 막는다. ip는 X-Forwarded-For에서
            // 복원될 수 있는 값이므로(forward-headers-strategy) 개행을 정제해 로그 위조를 막는다.
            if (updated.count() == MAX_ATTEMPTS + 1) {
                log.warn("로그인 요청 제한 초과로 차단 시작: ip={}, path={}, {}분 내 {}회째 시도",
                        CrlfUtils.forLog(ip), request.getRequestURI(), WINDOW.toMinutes(), updated.count());
            }
            response.setStatus(429);                                       // ← 핵심: 여기서 차단
            response.setContentType("application/json;charset=UTF-8");
            response.getWriter().write("{\"message\":\"요청이 너무 많습니다. 잠시 후 다시 시도해주세요.\"}");
            return;
        }

        chain.doFilter(request, response);
    }
}

❓ 소프트웨어·데이터 무결성 실패란?

우리 서비스는 우리가 짠 코드만으로 돌아가지 않습니다. Maven/npm 라이브러리, Docker 이미지, 배포 파이프라인(CI/CD)처럼 외부에서 받아오는 것들 위에서 돌아갑니다. 이때 받아온 것이 변조되지 않았는지 확인하는 절차 없이 무조건 신뢰하고 실행하면, 공격자가 그 공급 경로(공급망)를 한 번만 오염시켜도 우리 서버 전체가 넘어갑니다. 이것이 무결성 실패입니다.

🔍 우리 프로젝트에서 찾은 "검증 없이 신뢰하던 지점" 2곳

코드·의존성·배포 경로를 무결성 관점에서 하나씩 훑어보니, 받아온 것을 확인 없이 그대로 믿고 실행하는 지점이 2곳 있었습니다. 아래에서 하나씩 해결합니다.

  • ① docker-compose가 adminer:latest처럼 내용이 언제든 바뀔 수 있는 태그로 이미지를 받음
  • ② 빌드 때 받아오는 라이브러리(Maven/npm)의 체크섬이 틀려도 그대로 통과됨
① "어제 받은 프로그램과 오늘 받은 프로그램이 다를 수 있다" — Docker 이미지 digest 고정 (docker-compose.yml)

digest란 이미지 내용 전체를 요약한 sha256 지문입니다. 태그(latest, 8.0)는 "이름표"라서 가리키는 내용물이 바뀔 수 있지만, digest는 내용이 1바이트만 달라져도 값이 완전히 달라집니다.

📖 이런 상황이 있었습니다

우리 DB 관리 도구인 Adminer를 docker-compose.yml에서 adminer:latest로 받고 있었습니다. latest는 "그 순간 가장 최신"이라는 이름표일 뿐이라, 오늘 pull한 이미지와 다음 달 pull한 이미지의 내용물이 다를 수 있고, 무엇이 달라졌는지 검증하는 절차도 없습니다.

만약 Docker Hub의 Adminer 배포 계정이 해킹당해 악성 이미지가 올라오면(실제로 인기 이미지 계정 탈취 사고가 여러 번 있었습니다), 우리는 다음 docker compose pull 때 그 악성 코드를 아무 확인 없이 실행하게 됩니다. 심지어 Adminer는 DB 접속 정보를 다루는 컨테이너라 피해가 가장 큰 자리입니다. DB인 mysql:8.0도 마이너 버전이 계속 바뀌는 "움직이는 태그"라 같은 문제가 있습니다.

1단계 — 지금 쓰는 이미지의 digest 확인 (터미널)

# 출력 예: mysql@sha256:04f3...(64자리 지문)

services:
  mysql:
    # 태그 뒤에 @sha256:... 을 붙이면 Docker는 태그가 아니라 digest로 검증한다
    # (태그는 사람이 읽기 위한 주석 역할로 남겨둔다)
    image: mysql:8.0@sha256:7dcddc01f13bab2f15cde676d44d01f61fc9f99fe7785e86196dfc07d358ae2b

  adminer:
    # latest 태그 제거 → 검증된 지문으로만 실행
    image: adminer@sha256:043db066c4532719f49e35355a620f0bbe48fc862f6bfccda72f441b162f092e
✨ 결론

이미지 주소 뒤에 @sha256 지문을 붙이는 것만으로, 공급자 쪽에서 이미지가 바꿔치기되어도 우리 서버는 pull 단계에서 거부하게 되었습니다. 업데이트가 필요할 때는 새 버전의 지문을 확인하고 우리가 직접 지문을 갱신합니다 — 즉 "자동으로 바뀌는 것"에서 "우리가 승인해야 바뀌는 것"으로 통제권이 넘어왔습니다.

💡 핵심 정리
  • 태그 = 이름표 (내용물이 바뀔 수 있음) / digest = 내용물의 지문 (바뀌면 값이 달라짐)
  • backend/frontend의 Dockerfile 베이스 이미지(maven:3.9, node:20-alpine 등)도 같은 원리로 고정할 수 있음 (심화)
  • digest를 고정하면 업데이트를 놓칠 수 있으므로, dependabot.yml에 docker 생태계를 추가해 새 지문 갱신 PR을 자동으로 받는 것까지가 한 세트

❓ CRLF 로그 위조(Log Forging)란?

사용자가 입력한 데이터를 그대로 로그에 남기는 취약점을 이용해, 개행 문자(CRLF: \r\n)를 주입하여 가짜 로그 줄을 만들어내는 공격입니다.

⚠️ 개행 문자가 로그 위조에 악용되는 이유

서버는 로그 파일에 기록을 남길 때 "개행 문자가 나오면 이번 줄은 끝났고, 다음 줄부터 새 기록이다"라고 인식합니다.

공격자가 입력창에 글을 쓰다가 의도적으로 이 개행 문자(\r\n)를 섞어 넣으면, 서버는 사용자가 엔터를 친 것으로 착각하여 하나의 로그를 두 개의 로그인 것처럼 쪼개서 저장하게 됩니다. 이 때문에 시스템 오류나 해킹 흔적을 조작하는 '로그 위조'가 가능해집니다.

프론트엔드 프로젝트의 .env 파일에 VITE_TURNSTILE_SITE_KEY 환경변수를 추가하고 Cloudflare에서 발급받은 Site Key를 설정했습니다. 변경된 환경변수를 적용하기 위해 개발 서버를 다시 실행했습니다.

frontend/.env — Turnstile Site Key 환경변수 설정
환경변수 설정 전 — Turnstile 인증 불가 / 버튼 비활성화
환경변수 설정 후 — Turnstile 인증 성공 / 버튼 활성화
✅ 적용 결과

환경변수를 설정하고 개발 서버를 다시 실행한 결과, Turnstile 인증 화면에서 성공!이 표시되고 기존에 사용할 수 없었던 지점 등록 버튼도 정상적으로 활성화되는 것을 확인했습니다.

💡 핵심 정리
  • 브라우저 개발자 도구로 프론트엔드 보안 기능을 실제 실행 환경에서 점검했습니다
  • Turnstile 기능은 구현되어 있었지만 VITE_TURNSTILE_SITE_KEY 환경변수가 누락되어 인증이 동작하지 않았습니다
  • .env에 Site Key를 추가하고 개발 서버를 재시작해 변경된 환경변수를 적용했습니다
  • 수정 후 Turnstile 인증 성공과 지점 등록 버튼 활성화를 직접 확인했습니다
⚠️ 검증 범위와 한계

검증 범위: Site Key 전달, Turnstile 토큰 생성, 지점 등록 버튼 활성화를 브라우저에서 확인했습니다.

한계: Site Key는 공개되어도 되는 값이지만 Secret Key는 프론트엔드에 노출하면 안 됩니다. 실제 보안 검증을 완성하려면 백엔드가 Cloudflare에 토큰을 전달해 서버 측 검증을 수행해야 합니다.
