A01:2025

접근 통제 실패 (Broken Access Control)

로그인한 사람이 "볼 자격이 있는 것만" 보게 하는 통제가 무너지는 문제

① 토큰 버전을 관리해 로그아웃된 사용자의 기존 토큰이 더 이상 유효하지 않도록 차단
📖 이런 상황이 있었다

지점 관리자는 매장 계산대 옆 공용 PC에서 관리자 화면에 로그인 후 업무를 처리하고, 업무가 종료되면 로그아웃 버튼을 누른 뒤 자리를 비웁니다. 일반적으로 사용자는 로그아웃과 동시에 해당 로그인 상태가 종료되었다고 인식합니다.

그런데 점검해 보니 로그아웃을 누른 뒤에도, 로그아웃 직전에 복사해 둔 토큰으로 매출·재고·주문 조회 API가 그대로 200을 응답하고 있었다. 점장 본인이 다시 로그인해서 새 토큰을 발급받아도, 브라우저를 닫아도 막히지 않았다.

🚨 문제점 분석

원인은 로그아웃이 브라우저 안에서만 일어나는 동작이었기 때문이다. 기존 로그아웃은 저장된 토큰 문자열을 로컬 스토리지에서 지우는 것이 전부였고 서버에는 아무 요청도 보내지 않았다.

로그인 토큰은 서버에 세션을 저장하지 않는 방식이라, 서버 입장에서는 서명과 만료 시각만 맞으면 유효한 토큰이다. 누가 로그아웃했는지 판단할 근거 자체가 서버에 없었고, 그래서 발급된 토큰은 발급 후 12시간 동안 무조건 살아 있었다.

즉 토큰을 한 번 복사해 둔 사람은 그 뒤로 브라우저도 비밀번호도 없이 그 계정 권한을 그대로 쓸 수 있었고, 서버에는 이를 되돌릴 수단이 하나도 없는 상태였다.

  localStorage.removeItem('hq-session')   // 브라우저에서 문자열만 삭제
  router.replace('/branch/login')          // 서버에는 알리지 않음

🔧 적용 사항

1. AdminTokenService.java — 계정별 토큰 버전을 두고, 토큰 발급 시 그 번호를 payload에 함께 넣어 서명.
2. AdminTokenService.java — 토큰 검증 순서에 서명 확인 → 만료 확인 → 세대 대조를 추가해, 세대가 다르면 거부.
3. LogoutController.java — 로그아웃 API를 신설해 호출 시 해당 계정의 세대 번호를 +1하고 인증 쿠키를 삭제.

AdminTokenService.java (세대 카운터) — 실제 적용 코드 ①
// adminId -> 현재 토큰 버전. 없으면 0버전.
private final Map<Long, Integer> tokenVersions = new ConcurrentHashMap<>();

/** 이 관리자에게 발급된 모든 토큰을 즉시 무효화한다(로그아웃, 탈취 대응). */
public void revokeAll(Long adminId) {
    tokenVersions.merge(adminId, 1, Integer::sum);   // 원자적 +1
}

public String issue(Long adminId) {
    // 발급 당시의 버전을 payload에 함께 넣어 서명한다 → 값을 되돌리면 서명이 깨진다
    return sealed(adminId + ":" + currentVersion(adminId) + ":" + expiresIn(VALID_DURATION));
}

// 검증할 때: 서명 확인 → 만료 확인 → 버전 대조
if (Integer.parseInt(parts[offset + 1]) != currentVersion(adminId)) return null;
LogoutController.java (로그아웃 API 신설) — 실제 적용 코드 ②
@PostMapping("/logout")
public void logout(@RequestHeader(value = "Authorization", required = false) String authorization,
                   HttpServletResponse response) {
    authCookie.clear(response);                       // 쿠키 삭제 (JS는 못 지운다)
    if (authorization == null || !authorization.startsWith("Bearer ")) return;

    Long adminId = adminTokenService.verify(authorization.substring(7));
    if (adminId != null) adminTokenService.revokeAll(adminId);   // 버전 +1
}
🧪 실제 테스트 실행

로그인해서 토큰을 확보한 뒤 ① 조회 → ② 로그아웃 → ③ 같은 토큰으로 재조회 순서로 호출하는 스크립트 (token-revocation-curl-test.sh)를 만들어, 적용 전과 적용 후의 응답 코드를 같은 조건에서 비교했다.

❌ 적용 전 — 로그아웃이 무의미

①에서 로그인하면 토큰이 응답 본문에 그대로 담겨 온다. 화면 스크립트가 읽어 보관할 수 있는 값이다. ③에서 로그아웃을 호출하면 404가 돌아온다 — 서버에 로그아웃 API 자체가 없어서, 로그아웃이란 브라우저가 저장된 문자열을 지우는 것이 전부였다.

그래서 ④에서 아까 그 토큰을 그대로 다시 넣으면 여전히 200이 응답된다. 서버는 이 토큰이 로그아웃된 것인지 알 방법이 없고, 이 상태가 만료까지 12시간 그대로 이어진다.

✅ 적용 후 — 즉시 무효화

①의 응답을 보면 토큰이 본문이 아니라 Set-Cookie로 내려오고, HttpOnly가 붙어 있어 화면 스크립트가 값을 읽을 수 없다. ③에서 로그아웃이 200으로 처리되며, 이때 서버가 해당 계정의 세대 번호를 올린다.

그 결과 ④에서 같은 쿠키를 그대로 다시 보내면 401로 거부된다. 서명도 멀쩡하고 만료도 안 됐지만, 토큰에 서명돼 있는 세대 번호가 서버의 현재 값과 달라서 통과하지 못한다.

✨ 결론

로그아웃의 기준점을 브라우저에서 서버로 옮겼다. 이제 로그아웃은 저장된 문자열을 지우는 동작이 아니라, 서버가 그 토큰의 버전 번호를 올려 이전에 발급된 토큰 전부를 한 번에 무효로 만드는 동작이다.

그 결과 공용 PC에서 토큰이 유출됐더라도 로그아웃 한 번으로 회수가 가능해졌고, 토큰 탈취가 의심될 때 12시간 만료를 기다릴 필요 없이 즉시 대응할 수 있는 수단이 생겼다.

💡 핵심 정리
  • 로그아웃은 토큰을 브라우저에서 지우는 것이 아니라 토큰을 서버에서 무효화하는 것이어야 합니다.
  • 토큰 버전 번호도 서명 대상이므로, 공격자가 토큰의 버전 값을 되돌리면 서명이 일치하지 않아 서버에서 요청이 거부됩니다.
  • 한 사람의 로그아웃이 다른 관리자 토큰에는 영향을 주지 않습니다 (계정별 카운터)
A02:2025

보안 설정 오류 (Security Misconfiguration)

프로그램은 정상적으로 작동하지만, 보안 설정이 허술해서 공격받기 쉬워지는 문제

① 관리자·키오스크 화면에서만 API 응답을 읽도록 CORS 제한
📖 이런 상황이 있었다

관리자 화면은 서버의 API를 호출해 상품·재고·주문 정보를 가져온다. 개발 중에는 관리자 화면의 주소와 포트가 자주 바뀌었고, 주소가 변경될 때마다 허용 목록을 수정하는 불편을 줄이기 위해 모든 웹사이트의 API 응답 접근을 허용하는 * 설정을 사용했다.

이 설정이 운영 서버에도 유지되면 키오스크 서비스와 관계없는 웹사이트도 API 응답을 읽을 수 있다. 예를 들어 관리자가 로그인한 상태에서 공격자가 보낸 링크를 열면, 공격 사이트는 관리자 브라우저를 이용해 키오스크 API를 호출한다. 브라우저는 관리자에게 발급된 인증 정보를 요청에 함께 전송하므로, 모든 사이트가 허용된 상태에서는 공격 사이트가 상품·재고·주문 정보를 읽을 수 있다.

🚨 문제점 분석

CORS는 어떤 웹사이트가 브라우저에서 API 응답을 읽을 수 있는지 정하는 규칙이다. 모든 출처를 허용하면 공격 사이트도 관리자 API의 응답을 읽을 수 있으므로, 실제 관리자 화면과 키오스크 화면의 주소만 허용해야 한다. 또한 CORS는 사용자 인증 기능이 아니므로 API의 로그인 인증과 관리자 권한 검사도 별도로 유지해야 한다.

📍 상황로그인한 관리자가 외부 사이트의 링크를 실행
→
🚨 문제모든 사이트를 허용해 공격 사이트도 관리자 API 응답을 읽음
→
🔧 적용개발·운영 환경별로 허용할 화면 주소만 목록에 등록
→

문제가 있었던 코드 — SecurityConfig.java
CorsConfiguration configuration = new CorsConfiguration();
configuration.addAllowedOriginPattern("*"); // 모든 Origin 허용
configuration.setAllowCredentials(true);
configuration.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE", "OPTIONS"));

// 운영 환경에서도 악성 사이트에 CORS 응답을 허용할 수 있음
🔧 적용 사항

1. application.yml — 개발·운영 환경별로 허용할 관리자·키오스크 Origin 목록을 분리해 설정.
2. SecurityConfig.java — 모든 출처를 허용하던 * 설정을 제거하고 setAllowedOriginPatterns(originPatterns)로 허용 목록만 등록.
3. SecurityConfig.java — 자격 증명 사용 여부와 허용 메서드·헤더를 명시해 등록되지 않은 Origin에는 CORS 허용 헤더를 반환하지 않도록 변경.

SecurityConfig.java — 실제 적용 코드
@Value("${app.cors.allowed-origin-patterns}")
private List<String> originPatterns;

CorsConfiguration configuration = new CorsConfiguration();
configuration.setAllowedOriginPatterns(originPatterns); // * 대신 허용 목록
configuration.setAllowCredentials(true);
configuration.setAllowedMethods(List.of("GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS"));
configuration.setAllowedHeaders(List.of("Authorization", "Content-Type"));
🧪 실제 테스트 실행
❌ 적용 전 — 모든 출처 허용되어 미등록 출처도 통과
적용 후 — 등록된 출처만 허용, 허용 목록 외 차단
✨ 결론

개발 편의를 위한 전체 허용 설정을 없애고 실제 관리자 화면과 키오스크 주소만 허용 목록에 넣었다. 이제 공격 사이트가 API 요청을 보내더라도 등록된 주소가 아니면 브라우저가 응답 내용을 읽지 못한다. CORS는 요청 자체를 막는 기능이 아니므로 로그인 인증과 관리자 권한 검사는 API에서 별도로 확인한다.

💡 핵심 정리
  • 모든 출처 허용 대신 환경별로 관리하는 허용 목록을 사용한다
  • 자격 증명을 사용하는 요청은 특히 출처를 좁게 제한해야 한다
  • CORS는 브라우저 정책이므로 API 인증과 권한 검사는 별도로 유지해야 한다
② Nginx 보안 헤더로 정상 화면 위에 투명한 공격 화면을 겹쳐 사용자가 의도하지 않은 버튼이나 링크를 누르게 만드는 공격과 잘못된 파일 실행 방지
📖 이런 상황이 있었다

Nginx는 화면과 API를 정상적으로 전달하고 있었지만, 브라우저가 지켜야 할 보안 규칙은 보내지 않고 있었다. 이 상태에서는 공격 사이트가 관리자 화면을 투명한 프레임으로 덮어 사용자가 엉뚱한 버튼을 누르게 하거나, 브라우저가 파일 형식을 잘못 판단해 실행할 수 있다.

그래서 Nginx 응답에 Content-Security-Policy, X-Frame-Options, X-Content-Type-Options 등의 헤더를 추가했다. 이제 브라우저는 허용된 리소스만 불러오고, 다른 사이트가 관리자 화면을 프레임에 넣거나 파일 형식을 임의로 판단하는 동작을 차단한다.

🚨 문제점 분석

보안 헤더가 없으면 다른 사이트가 관리자 화면을 프레임에 삽입하거나 브라우저가 파일 형식을 임의로 추측할 수 있어 클릭재킹과 의도하지 않은 콘텐츠 실행 위험이 커진다.

server {
  listen 80;

  location / {
    try_files $uri $uri/ /index.html;
  }

  # CSP, X-Frame-Options, nosniff 등 보안 헤더가 없음
}
🔧 적용 사항

1. nginx.conf — Content-Security-Policy를 추가해 허용할 리소스 출처와 프레임 삽입 범위를 제한.
2. nginx.conf — X-Frame-Options와 X-Content-Type-Options를 추가해 클릭재킹과 MIME 타입 추측을 차단.
3. nginx.conf — Referrer-Policy와 Permissions-Policy를 모든 응답에 always 옵션으로 적용.

nginx.conf — 실제 적용 코드
add_header Content-Security-Policy
  "default-src 'self'; object-src 'none'; frame-ancestors 'self'" always;
add_header X-Frame-Options "SAMEORIGIN" always;
add_header X-Content-Type-Options "nosniff" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
add_header Permissions-Policy "camera=(), microphone=(), geolocation=()" always;

✨ 결론

브라우저가 허용된 리소스와 표시 방식만 사용하도록 제한해 클릭재킹과 잘못된 파일 실행 위험을 줄였다.

💡 핵심 정리
  • CSP로 허용할 리소스 출처와 프레임 삽입 범위를 제한한다
  • nosniff로 브라우저가 파일 형식을 추측해 실행하지 못하게 한다
  • 헤더는 취약한 코드를 고치는 대신이 아니라 피해를 줄이는 추가 방어선이다
⚠️ 검증 범위와 한계

검증 범위: SecurityConfig의 허용 Origin 목록과 Nginx의 CSP·X-Frame-Options·nosniff 등 보안 헤더 설정을 확인한다. 브라우저에서 허용된 Origin에는 CORS 헤더가 나오고, 미등록 Origin에는 나오지 않는지도 비교한다.

한계: CORS는 브라우저가 응답을 읽는 것을 제한할 뿐 curl·Postman 요청 자체를 막지 않는다. API 인증·권한 검사와 HTTPS는 별도로 필요하며, CSP도 XSS 취약 코드 자체를 제거하는 방어는 아니다.

소프트웨어 공급망 실패 (Software Supply Chain Failures)

라이브러리·빌드·배포 등 소프트웨어를 만들고 전달하는 모든 과정에서 발생할 수 있는 보안 문제

① 시크릿(비밀번호·API 키)을 Git에 올리지 않기 — .env.example
📖 이런 상황이 있었습니다

아이스크림 키오스크를 만들면서 데이터베이스 비밀번호, 결제 API 키, Firebase 키 같은 중요한 비밀값들을 코드와 함께 Git 저장소에 그대로 올렸고, GitHub나 GitLab 같은 플랫폼에 코드가 올라가면 이를 모니터링하는 악성 봇들의 표적이 되기 때문에, 비밀번호와 키가 해커에게 탈취되어 결제 API가 무단으로 사용되는 문제가 생길 수 있습니다. 심지어 나중에 지워도 이미 커밋 기록에 영구적으로 남아있어 완전히 없앨 수가 없습니다.

🚨 문제점 분석

원인은 설정 파일에 실제 값을 직접 적어두고 그 파일을 그대로 커밋했기 때문입니다. 비밀값이 코드와 같은 취급을 받으면, 저장소에 접근할 수 있는 사람 전원이 곧 그 비밀값을 아는 사람이 됩니다.

더 큰 문제는 되돌릴 수 없다는 점입니다. Git은 파일을 지워도 커밋 기록에 원본이 그대로 남기 때문에, 나중에 삭제 커밋을 올려도 히스토리를 되짚으면 값이 복원됩니다. "실수를 알아차리고 지우면 된다"가 통하지 않는 종류의 사고입니다.

그 결과 저장소가 통째로 유출되더라도 그것만으로는 DB나 결제 API에 접근할 수 없고, 팀원이 실수로 커밋하려 해도 .gitignore가 먼저 걸러냅니다.

💡 핵심 정리
  • .env (실제 비밀값) → .gitignore 처리 → Git에 절대 올라가지 않음
  • .env.example (안내용) → "이런 변수가 필요하다"는 가이드만 Git에 올림

코드가 바뀔 때마다 자동으로 서버에 배포되는 시스템(CI/CD)을 만들었습니다. 그런데 배포 스크립트에 서버 접속 SSH 키, AWS 접속 키를 코드에 직접 써넣으면 저장소를 볼 수 있는 팀원 누구나, 심지어 퇴사한 팀원도 서버 비밀번호를 알게 됩니다.

또한 배포에 쓰는 AWS 계정에 관리자 권한을 전부 주면, 해커가 CI/CD 파이프라인을 뚫었을 때 서버 전체, 데이터베이스 전체를 마음대로 삭제하거나 데이터를 가져갈 수 있습니다.

🚨 문제점 분석

배포 스크립트도 결국 저장소에 커밋되는 코드입니다. 여기에 키를 적으면 ①번과 똑같은 문제가 배포 파이프라인에서 반복됩니다. 오히려 파이프라인은 외부 러너에서 실행되고 실행 로그까지 남아 노출 경로가 더 넓습니다.

여기에 권한 문제가 겹칩니다. 배포에 필요한 일은 인스턴스를 켜고 IP를 조회하는 것뿐인데 관리자 권한 키를 그대로 쓰고 있었습니다. 이러면 키 하나가 유출되는 순간 그 피해 범위가 배포가 아니라 계정 전체가 됩니다.

비밀을 숨기는 것과 비밀이 할 수 있는 일을 줄이는 것, 두 가지를 함께 적용했습니다. 키는 코드에서 사라졌고, 남은 키마저 권한이 좁아졌습니다.

그래서 저장소를 열람할 수 있어도 실제 값은 볼 수 없고, 설령 파이프라인이 탈취되더라도 그 키로는 인스턴스를 켜고 IP를 조회하는 것 외에는 아무것도 할 수 없습니다.

💡 핵심 정리
  • 코드에는 $DB_PASSWORD 같은 변수 참조만 → 저장소를 봐도 실제 비밀번호 모름
  • AWS 키는 서버 시작·IP 조회 딱 2가지 권한만 가진 전용 계정 사용 → 파이프라인이 해킹당해도 데이터 삭제·유출 불가
  • 이것을 최소 권한 원칙(Principle of Least Privilege)이라고 합니다
③ 배포한 서버가 어떤 코드인지 추적하기 — 커밋 SHA 기반 Docker 이미지 태그
📖 이런 상황이 있었습니다

아이스크림 키오스크를 자동 배포하면서 Docker 이미지 태그를 :latest로만 써서 배포했더니, 서버에 문제가 생겼을 때 "지금 서버에 떠있는 게 어제 코드야? 오늘 코드야?"를 알 수가 없었습니다.

그래서 이전 버전으로 되돌리려 해도 어느 시점으로 돌아가야 할지 알 수 없어 혼란이 생겼습니다.

🚨 문제점 분석

:latest는 고정된 이름이지 고정된 내용이 아닙니다. 빌드할 때마다 같은 태그에 새 이미지를 덮어쓰기 때문에, 태그만 봐서는 그 안에 어떤 코드가 들어 있는지 알 수 없습니다.

이건 장애 대응만의 문제가 아니라 공급망 무결성의 문제입니다. 배포된 이미지와 소스 커밋을 연결할 수 없으면, 누군가 같은 태그로 다른 이미지를 밀어 넣어도 바뀌었다는 사실 자체를 알아차릴 수 없습니다.

📍 상황코드를 고칠 때마다 서버에 자동 배포
→
🚨 문제:latest 태그만 쓰면 어떤 코드가 떠있는지 모름
→
🔧 적용이미지 태그를 커밋 해시(SHA)로 고정
→
✅ 결과문제 발생 시 즉시 소스 역추적 + 빠른 롤백
문제가 되는 코드 — 흔히 쓰는 :latest 방식 (우리 저장소에는 없었음)
# 자동 배포를 처음 붙일 때 가장 많이 쓰는 형태
build-backend:
  script:
    - docker build -t kiosk/backend:latest backend
    - docker push kiosk/backend:latest      # ← 매번 같은 태그에 덮어쓴다

deploy-backend:
  script:
    - docker pull kiosk/backend:latest      # ← 무엇을 받는지 태그만 봐서는 알 수 없다

# 태그 이름은 고정이지만 그 안의 내용은 배포할 때마다 달라진다.
# → 지금 서버에 떠 있는 것이 어느 커밋인지 되짚을 방법이 없다.
🔧 적용 사항

1. .gitlab-ci.yml — 이미지 태그를 :latest 대신 커밋 해시 변수 $CI_COMMIT_SHORT_SHA로 지정.
2. 빌드·배포 job이 같은 변수를 참조하게 해서, 빌드한 이미지와 배포되는 이미지가 어긋날 수 없도록 함.
3. backend·frontend 두 이미지에 동일 규칙을 적용.

.gitlab-ci.yml — 실제 적용 코드
variables:
  # $CI_COMMIT_SHORT_SHA = Git 커밋 고유 번호 7자리 (예: a1b2c3d)
  # 이 값이 이미지 태그가 되면 언제나 추적 가능
  BACKEND_IMAGE:  $CI_REGISTRY_IMAGE/backend:$CI_COMMIT_SHORT_SHA
  FRONTEND_IMAGE: $CI_REGISTRY_IMAGE/frontend:$CI_COMMIT_SHORT_SHA

build-backend:
  script:
    - docker build -t $BACKEND_IMAGE backend   # → kiosk/backend:a1b2c3d
    - docker push $BACKEND_IMAGE               # → 고유 태그로 레지스트리 저장
🧪 적용 전후 비교

🚨 문제점 분석

암호화 실패 (Cryptographic Failures)

민감한 값이 보호되지 않은 채 저장·전송·기록되는 문제 — 암호를 안 쓰는 것뿐 아니라 잘못 쓰는 것도 포함된다

① 1분짜리 스트림 전용 토큰을 사용해 실시간 알림 토큰이 서버 로그에 노출되지 않도록 방지
📖 이런 상황이 있었다

지점 대시보드는 새 주문이 들어오면 즉시 알림을 띄우기 위해 SSE(Server-Sent Events)로 서버와 연결을 유지한다. 그런데 브라우저의 EventSource는 커스텀 헤더를 보낼 수 없다. 그래서 로그인 토큰을 주소창(URL 쿼리 파라미터)에 실어 보낼 수밖에 없었다.

문제는 Tomcat 액세스 로그가 쿼리스트링을 포함한 요청 주소 전체를 기록한다는 점이었다. 즉 12시간 동안 그 지점 계정으로 뭐든 할 수 있는 토큰이 로그 파일에 평문으로 30일간 보관되고 있었다. 로그를 볼 수 있는 사람이라면 누구나 그 값을 복사해 쓸 수 있는 상태였다.

🚨 문제점 분석

${} 문자열 치환은 외부 입력을 SQL 본문에 직접 결합하므로, 공격 문자열이 조회 조건 자체를 바꿀 수 있다.

✨ 결론

기술적 제약(EventSource는 헤더를 못 보냄)은 그대로 두고, URL에 실리는 값의 권한과 수명을 줄이는 쪽으로 풀었다. 로그에 값이 남는 것 자체는 여전하지만, 남는 값이 60초짜리 스트림 전용 토큰으로 바뀌었다.

💡 핵심 정리
  • URL에 실리는 값은 반드시 로그에 남는다고 가정해야 한다
  • 기술적 제약(EventSource는 헤더 불가)을 없앨 수 없다면, 실리는 값의 권한과 수명을 줄이는 방향으로 푼다
  • 토큰은 접두사가 달라 양방향으로 분리된다 — 로그인 토큰으로 스트림도 열 수 없다
② httpOnly 쿠키로 전환해 JavaScript가 로그인 토큰을 읽지 못하도록 방지

HqUploadService.java — 실제 적용 코드
@Service
public class HqUploadService {

    private static final Set ALLOWED_EXTENSIONS = Set.of("png", "jpg", "jpeg");

    // 확장자별로 허용되는 실제 MIME 타입 (매직바이트 기준)
    private static final Map> ALLOWED_MIME_TYPES_BY_EXTENSION = Map.of(
            "png", Set.of("image/png"),
            "jpg", Set.of("image/jpeg"),
            "jpeg", Set.of("image/jpeg")
    );

    private static final ContentInfoUtil CONTENT_INFO_UTIL = new ContentInfoUtil();

    @Value("${app.upload.dir}")
    private String uploadDir;

    public String store(MultipartFile file) {
        if (file == null || file.isEmpty()) {
            throw new IllegalArgumentException("업로드할 파일이 없습니다.");
        }

        String originalName = file.getOriginalFilename();

        String extension = getExtension(originalName);

        if (!ALLOWED_EXTENSIONS.contains(extension)) {
            throw new IllegalArgumentException(
                    "PNG, JPG, JPEG 파일만 업로드할 수 있습니다."
            );
        }

        try {
            byte[] content = file.getBytes();

            validateActualContentType(content, extension);

            Path uploadPath = Paths.get(uploadDir)
                    .toAbsolutePath()
                    .normalize();

            // 파일이 없으면 생성
            Files.createDirectories(uploadPath);

            // UUID 기반 신규 파일명 생성
            String storedFilename = UUID.randomUUID()
                    + "."
                    + extension;

            Path target = uploadPath.resolve(storedFilename)
                    .normalize();

            // 최종 경로 검증 (추가 방어)
            if (!target.startsWith(uploadPath)) {
                throw new SecurityException("잘못된 파일 경로입니다.");
            }

            Files.write(target, content);

            return "/uploads/" + storedFilename;

        } catch (IOException e) {
            throw new RuntimeException(
                    "이미지 업로드에 실패했습니다.",
                    e
            );
        }
    }


// 파일 확장자가 아닌 실제 바이너리 시그니처(매직바이트)로 이미지 타입을 검증한다.
    private void validateActualContentType(byte[] content, String extension) throws IOException {
        ContentInfo contentInfo = CONTENT_INFO_UTIL.findMatch(content);
        String mimeType = contentInfo != null ? contentInfo.getMimeType() : null;

        Set allowedMimeTypes = ALLOWED_MIME_TYPES_BY_EXTENSION.get(extension);

        if (mimeType == null || allowedMimeTypes == null || !allowedMimeTypes.contains(mimeType)) {
            throw new IllegalArgumentException(
                    "파일 내용이 PNG, JPG, JPEG 이미지 형식이 아닙니다."
            );
        }
    }

// 짧은 시간 안에 너무 많은 요청이 오면 429로 막는다. Turnstile은 "사람인지"만 걸러낼 뿐

// 매장 전체가 한 번에 묶이지 않도록 임계치를 넉넉하게 잡았다.
// Spring Boot가 Filter 빈을 자동으로 서블릿 컨테이너에 등록해주므로 별도 설정은 필요 없다.
@Slf4j
@Component
public class LoginRateLimitFilter extends OncePerRequestFilter {

    private static final Set<String> LIMITED_PATHS = Set.of(
            "/api/hq-auth/login",
            "/api/branch-auth/db-login",
            "/api/branch-auth/firebase-session"
    );

    private static final int MAX_ATTEMPTS = 10;  // 10번 허용
    private static final Duration WINDOW = Duration.ofMinutes(5);  //5분

    private record Window(int count, Instant resetAt) {}

    private final ConcurrentHashMap<String, AtomicReference<Window>> attempts = new ConcurrentHashMap<>();

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response, FilterChain chain)
            throws ServletException, IOException {
    	if (!"POST".equals(request.getMethod())
    	        || !LIMITED_PATHS.contains(request.getRequestURI())) {
            chain.doFilter(request, response);
            return;
        }

        String ip = request.getRemoteAddr();
        AtomicReference<Window> ref = attempts.computeIfAbsent(ip,
                k -> new AtomicReference<>(new Window(0, Instant.now().plus(WINDOW))));

        Window updated = ref.updateAndGet(w -> Instant.now().isAfter(w.resetAt())
                ? new Window(1, Instant.now().plus(WINDOW))
                : new Window(w.count() + 1, w.resetAt()));

        if (updated.count() > MAX_ATTEMPTS) {
            // 무차별 대입 탐지용 보안 이벤트 기록. 윈도우당 처음 차단되는 순간에만 남겨
            // 공격 트래픽이 로그 자체를 폭주시키는 것을 막는다. ip는 X-Forwarded-For에서
            // 복원될 수 있는 값이므로(forward-headers-strategy) 개행을 정제해 로그 위조를 막는다.
            if (updated.count() == MAX_ATTEMPTS + 1) {
                log.warn("로그인 요청 제한 초과로 차단 시작: ip={}, path={}, {}분 내 {}회째 시도",
                        CrlfUtils.forLog(ip), request.getRequestURI(), WINDOW.toMinutes(), updated.count());
            }
            response.setStatus(429);                                       // ← 핵심: 여기서 차단
            response.setContentType("application/json;charset=UTF-8");
            response.getWriter().write("{\"message\":\"요청이 너무 많습니다. 잠시 후 다시 시도해주세요.\"}");
            return;
        }

        chain.doFilter(request, response);
    }
}

보안 로깅 및 모니터링 실패 (Security Logging and Monitoring Failures)

공격이 일어났을 때 알아차리고 추적할 수 있는 능력

① 로그에 가짜 기록 심기 공격 차단 — CRLF 로그 위조 전역 방어 (logback-spring.xml)
CRLF: CR(\r)과 LF(\n)을 합친 줄바꿈 문자
· 로그 위조(Log Forging): 입력값에 줄바꿈을 섞어 없던 로그 줄을 지어내는 공격
📖 이런 상황이 있었다

아이스크림 키오스크에서 curl로 로그인 API를 호출할 때, 아이디 입력값에 특수한 줄바꿈 문자(\r\n)를 넣어서 요청을 보냈다.

서버가 이 아이디를 그대로 로그에 남기자, 줄바꿈 문자 때문에 로그 파일에 가짜 줄이 만들어졌다. 예를 들어 로그 파일에 [INFO] 관리자 권한 획득 성공이라는 줄이 생기는데, 이건 실제가 아니라 해커가 심어놓은 가짜 로그이다.

이런 가짜 로그가 있으면 보안 담당자가 로그를 확인할 때 진짜 공격 기록을 찾기 어려워지고, 반대로 없는 사건이 있었던 것처럼 속일 수도 있다.

🚨 문제점 분석

원인은 사용자가 보낸 값을 로그에 그대로 이어 붙였다는 점이다. 로그 파일에서 한 줄은 곧 하나의 기록이고, 줄을 나누는 유일한 기준은 개행 문자이다.

그래서 입력값에 개행이 섞이면 서버는 그것을 "이 기록은 끝났다"는 신호로 읽고 다음 글자부터 새 기록으로 저장한다. 공격자가 로그의 내용이 아니라 구조를 조작할 수 있다는 뜻이다. 로그는 사고가 났을 때 사실 관계를 판단하는 근거인데, 그 근거 자체를 공격자가 쓸 수 있게 되는 셈이다.

💡 핵심 정리
  • CRLF 로그 위조 = 입력값에 줄바꿈(\r\n)을 넣어 없던 로그 줄을 지어내는 공격
  • 로그는 한 줄이 하나의 기록이라, 줄을 늘리면 그대로 가짜 기록이 된다
  • logback 설정 한 곳에서 전체 로그의 줄바꿈을 공백으로 치환 → 코드를 고치지 않아도 모든 로그에 자동 적용
  • 공격을 시도해도 로그가 항상 한 줄로만 출력되어 가짜 기록을 만들 수 없음
② 코드에서도 한 번 더 줄바꿈 제거 — CrlfUtils 심층 방어

특히 키오스크에서 Toss 결제나 Firebase 같은 외부 서비스의 응답 메시지도 로그에 남기는데, 이 외부 서비스가 보내준 응답에도 악성 줄바꿈이 있을 수 있다.

①의 logback 설정은 로그가 파일에 쓰이는 마지막 단계에서 동작한다. 잘 막아주지만, 뒤집어 보면 방어 전체가 설정 파일 한 줄에 의존하고 있다는 뜻이다.

누군가 로그 패턴을 손보거나 새 Appender를 추가하면서 그 부분을 빠뜨리면 방어가 통째로 사라지는데, 사라졌다는 사실을 알아차릴 방법이 없다. 로그는 평소에 아무도 들여다보지 않다가 사고가 났을 때 꺼내 보는 자료라, 구멍이 생겨도 한참 뒤에야 발견된다.

같은 공격을 서로 독립된 두 지점에서 막게 됐다. 코드에서 한 번(CrlfUtils), 로그가 파일에 쓰이는 마지막 단계에서 한 번(logback) 걸러진다.

두 방어는 서로를 전제하지 않기 때문에, 한쪽이 실수로 빠져도 나머지가 그대로 동작한다. 설정 파일 한 줄에 보안 전체가 걸려 있던 상태에서 벗어난 것이 이 항목의 목적이다.

🧪 CrlfUtils 방어 테스트 결과

총 3개 통과: CR·LF 제거, 단독 개행 제거, null 입력 처리가 모두 PASS했습니다.

📷 CRLF 로그 위조 방어 테스트 — 3/3 통과, Errors 0, Failures 0
💡 핵심 정리 — 심층 방어(Defense in Depth)
  • 1층 (logback 설정): 로그가 찍히는 마지막 단계에서 전역으로 줄바꿈 제거
  • 2층 (CrlfUtils): 로그를 남기는 코드에서 미리 제거 → 설정이 바뀌어도 안전
  • 두 계층이 독립적으로 동작 → 하나가 실패해도 나머지가 방어 = "두 겹 안전망"
③ 로그인 해킹 시도 탐지 & 차단 — LoginRateLimitFilter
📖 이런 상황이 있었다

키오스크 관리자 로그인 페이지에 curl로 요청을 보내면서 비밀번호를 하나씩 바꿔가며 초당 수백 번씩 자동으로 시도하는 공격(무차별 대입 공격)을 할 수 있다는 것을 알았다.

막는 코드가 없으면 시간만 충분하면 언젠가 맞는 비밀번호를 찾을 수 있고, 더 큰 문제는 이런 공격이 일어나도 서버 로그에 아무런 경고가 남지 않아 관리자가 해킹 시도를 전혀 모를 수 있다는 점이다.

이를 해결하기 위해 같은 IP에서 5분 안에 10번 넘게 로그인을 시도하면 자동으로 차단하고, 차단이 시작되는 순간에 경고 로그를 남기도록 했다. 이제 공격이 있으면 로그에 기록이 남아 나중에 확인하고 대응할 수 있게 되었다.

🚨 문제점 분석

로그인 API는 인터넷에 열려 있어야 하는 엔드포인트라 접근 자체를 막을 수 없다. 그런데 시도 횟수 제한이 없다 보니, 서버는 사람이 비밀번호를 잘못 친 것과 자동화 도구가 초당 수백 번 두드리는 것을 구분하지 않았다.

더 중요한 건 탐지 쪽이다. 실패한 로그인은 한 건씩 떼어놓고 보면 그냥 오타처럼 보인다. "같은 IP에서 5분 동안 수천 번"이라는 패턴을 보는 곳이 아무 데도 없었기 때문에, 공격이 진행 중이어도 알 수 없고 지나간 뒤에도 흔적이 남지 않았다. 이것이 A09가 다루는 탐지 실패에 해당한다.

3. 로그에 남기는 IP 값도 CrlfUtils로 정제 — 사용자가 조작할 수 있는 값이므로 ②의 방어를 여기서도 적용.
4. nginx 뒤에서는 모든 요청이 프록시 IP로 보이므로, X-Forwarded-For로 실제 클라이언트 IP를 복원해 집계.

// 로그인 3개 경로에만 적용 (다른 API는 정상 통과)
private static final Set<String> LIMITED_PATHS = Set.of(
        "/api/hq-auth/login",
        "/api/branch-auth/db-login",
        "/api/branch-auth/firebase-session"
);
private static final int MAX_ATTEMPTS = 10;           // 최대 10회
private static final Duration WINDOW = Duration.ofMinutes(5);  // 5분 기준

if (updated.count() > MAX_ATTEMPTS) {
    // 핵심 설계: 11번째 딱 한 번만 경고 로그 기록
    // → 공격 사실은 알 수 있되, 로그 파일이 수만 줄로 폭주하지 않음
    if (updated.count() == MAX_ATTEMPTS + 1) {
        // ip도 사용자 조작 가능한 값 → CrlfUtils로 줄바꿈 제거 후 로그 기록 (이중 방어)
        log.warn("로그인 요청 제한 초과로 차단 시작: ip={}, path={}, {}분 내 {}회째 시도",
                CrlfUtils.forLog(ip), request.getRequestURI(),
                WINDOW.toMinutes(), updated.count());
    }
    response.setStatus(429);   // Too Many Requests
    response.getWriter().write("{\"message\":\"요청이 너무 많습니다. 잠시 후 다시 시도해주세요.\"}");

}

✨ 결론

무차별 대입을 막는 것과 알아차리는 것을 함께 얻었다. 11회째부터 요청이 차단되므로 시간을 들여도 비밀번호를 맞힐 수 없고, 동시에 그 시점에 경고 로그가 남아 공격이 있었다는 사실 자체가 기록된다.

A09의 핵심은 차단이 아니라 사고를 알아차릴 수 있는가인데, 이 필터는 차단과 탐지를 한자리에서 처리한다. 이제 로그를 열면 "누가, 언제, 어디서 몇 번 시도했는지"가 남아 있다.

💡 핵심 정리
  • 무차별 대입 공격 = 비밀번호를 자동으로 수천 번 넣어보는 해킹 방법
  • 5분 안에 10번 초과하면 HTTP 429(차단) 응답 → 공격 자동 무력화
  • 차단 시작 시 딱 한 번만 경고 로그 기록 → 공격 탐지 가능하면서 로그 폭주 방지
  • IP 주소에도 CrlfUtils 적용 → 앞서 배운 로그 위조 공격을 여기서도 차단 (연쇄 방어)

A10:2025

예외 상황 처리 실패 (Mishandling of Exceptional Conditions)

비정상적인 입력을 안전하게 거부하지 않고 정상 처리로 이어가 잘못된 동작이 발생하는 문제

① 잘못된 재고 조정 유형을 정상 출고로 처리하는 Fail Open 문제
📖 이런 상황이 있었습니다

지점 관리자는 재고 수량을 직접 조정할 수 있으며, 백엔드의 BranchInventoryService.adjustInventory() 메서드에서 IN, OUT, SET과 같은 조정 유형에 따라 재고 수량을 계산하도록 구성되어 있습니다.

하지만 기존 코드에서는 IN과 SET만 명시적으로 처리하고, 그 외의 모든 값은 default 분기에서 재고 차감으로 처리하고 있었습니다. 따라서 존재하지 않는 유형이나 누락된 값도 오류로 거부되지 않고 정상적인 출고처럼 처리될 수 있는 상황이 있었습니다.

🚨 문제점 분석

예를 들어 type에 ABC와 같이 정의되지 않은 값을 전달하더라도 기존 로직에서는 default 분기로 진입해 요청한 수량만큼 재고를 차감할 수 있습니다. type이 null인 경우에도 빈 문자열로 변경된 뒤 동일하게 default 분기로 처리됩니다.

또한 grams 값에 대한 양수 검증이 없어 음수가 전달되면 계산 방향이 반대로 바뀔 수 있습니다. 예를 들어 재고가 6,000g인 상태에서 grams = -1000이 차감 로직으로 전달되면 6000 - (-1000) = 7000이 되어 오히려 재고가 증가할 수 있습니다.

이는 비정상적인 요청을 안전하게 거부하지 않고 정상 업무 처리로 이어가는 문제로, OWASP A10:2025의 대표 CWE 중 하나인 CWE-636: 안전하지 않은 실패(Failing Open)와 관련됩니다.

→

BranchInventoryService.java — 문제가 있었던 코드 
int grams = request.grams() == null ? 0 : request.grams();
int before = inventory.getCurrentQuantity();

int after = switch (request.type() == null ? "" : request.type()) {
    case "IN" -> before + grams;
    case "SET" -> Math.max(0, grams);
    default -> Math.max(0, before - grams);
};

// 문제점
// 1. "ABC"와 같은 잘못된 type도 default에서 재고 차감으로 처리됨
// 2. type이 null이어도 ""로 바뀐 뒤 default에서 처리됨
// 3. grams가 0 또는 음수여도 별도의 검증 없이 계산됨
🔧 적용 사항

1. 재고 조정 유형 검증 — IN, OUT, SET만 허용하고 그 외의 값이나 누락된 값은 IllegalArgumentException으로 거부합니다.
2. 조정 수량 검증 — grams가 null, 0, 음수인 경우 요청을 거부하여 잘못된 계산이 발생하지 않도록 합니다.
3. 명시적인 OUT 처리 — 재고 차감은 OUT인 경우에만 수행하고, 알 수 없는 값은 default에서 예외를 발생시켜 비정상 요청이 정상 업무 처리로 이어지지 않도록 합니다.

BranchInventoryService.java — 적용 코드 
public void adjustInventory(Long inventoryId,
                            InventoryAdjustRequest request,
                            Long branchId) {

    BranchInventory inventory = requireOwnedInventory(inventoryId, branchId);

    String type = request.type();
    Integer requestedGrams = request.grams();

    if (type == null ||
            !(type.equals("IN") || type.equals("OUT") || type.equals("SET"))) {
        throw new IllegalArgumentException("올바르지 않은 재고 조정 유형입니다.");
    }

    if (requestedGrams == null || requestedGrams <= 0) {
        throw new IllegalArgumentException("조정 수량은 1g 이상이어야 합니다.");
    }

    int grams = requestedGrams;
    int before = inventory.getCurrentQuantity();

    int after = switch (type) {
        case "IN" -> before + grams;
        case "OUT" -> Math.max(0, before - grams);
        case "SET" -> grams;
        default -> throw new IllegalArgumentException(
                "올바르지 않은 재고 조정 유형입니다."
        );
    };

    applyQuantity(inventory, after);

    // 이후 재고 변경 이력 저장 로직은 기존과 동일
}

✨ 결론

기존 재고 조정 로직은 알 수 없는 유형이나 누락된 값까지 기본 출고 처리로 이어질 수 있는 Fail Open 방식이었습니다.

이를 허용된 조정 유형과 수량을 먼저 검증하고, 비정상적인 요청은 예외로 중단하는 Fail Closed 방식으로 변경하여 잘못된 요청으로 재고가 임의 변경되는 상황을 방지하도록 구성했습니다.

💡 핵심 정리
  • 기존 코드에서는 알 수 없는 type과 null 값이 default 분기에서 재고 차감으로 처리될 수 있었습니다.
  • grams의 양수 검증이 없어 0 또는 음수 값에 따른 잘못된 재고 계산이 발생할 수 있었습니다.
  • IN, OUT, SET만 허용하고 비정상 입력은 400 Bad Request로 거부하도록 처리합니다.
  • 비정상 상황에서 임의의 기본 동작을 수행하지 않고 안전하게 실패하도록 하여 OWASP A10:2025의 CWE-636 Failing Open 위험을 줄입니다.
